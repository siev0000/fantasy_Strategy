# ワールドマップ・マルチプレイ ルーム設計

最終更新: 2026-09-24

対象: `siev0000/fantasy_Strategy`  
作業基準ブランチ: `ui/mobile-responsive-port-20260912`

> この文書は Phase E-2「ワールドマップのマルチプレイ」の実装設計をまとめる。
> 現在のゲームルールをマルチプレイ専用に作り直さず、既存の v39 ゲーム状態・移動・戦闘・ターン・AI 処理を再利用する。
> 初回プレイ形式では `シングル通常 / シングルテスト / マルチ通常` を分け、マルチプレイは常に通常プレイとして扱う。`テストゲーム状態.json` とテスト操作はマルチ経路へ持ち込まない。

---

## 1. 目的

シングルプレイ用ワールドマップを、複数プレイヤーが同じゲームへ参加して遊べるようにする。

基本導線:

```text
ルーム作成
  ↓
ルームID発行
  ↓
他プレイヤーがルームIDで参加
  ↓
担当 playerId を決定
  ↓
各プレイヤーが自分の担当勢力の開始種族を選択
  ↓
ホストがゲーム開始設定を共有
  ↓
全員準備完了
  ↓
ホストがゲーム開始
  ↓
テストデータを使わない空の players[] / factionState を作成
  ↓
共有ワールド生成・同期
  ↓
統治者作成（次段階で通信接続）
  ↓
初期村配置（次段階で通信接続）
  ↓
全勢力の初期配置完了後に通常ゲームへ
```

初期実装では公開ルーム一覧・自動マッチングは行わず、ルームID共有方式を採用する。

v39ロビーのプレイヤー名入力欄は、ルーム作成側では最初から `ホストプレイヤー`、参加側では最初から `プレイヤー1` を表示する。参加時に同名が存在する場合はサーバー側で末尾番号を付与または繰り上げて一意化する。手入力名も同一ルーム内で重複させない。再接続時は自分自身を重複判定から除外して表示名を維持し、ホスト移譲だけでは表示名を変更しない。

---

## 2. 現在存在する実装

現在すでに Node.js + Express + Socket.IO の通信基盤が存在する。

`server.js`:
- ルームID生成
- ルーム作成
- ルーム参加
- ルーム退出
- 接続プレイヤー一覧
- ルームチャット
- 簡易戦闘状態同期

`frontend/src/components/RoomModal.vue`:
- ルームID入力
- プレイヤー名入力
- 作成 / 参加 / 退出
- 参加者表示
- ルームチャット

`frontend/src/v39/core/v39-multiplayer-lobby.js`:
- プレイ形式選択でマルチプレイを選ぶと開く通信ロビー
- ルーム作成 / 参加 / 退出
- ホスト、参加者の接続・準備状態、操作勢力数、担当勢力の表示と変更
- ホストだけがロビーから共有ゲーム開始設定を保存
- `participantId + reconnectToken` による再接続

v39ロビーはStage 1に加えて、担当勢力ごとの開始種族選択、Stage 2のゲーム開始、Stage 3の初期フルスナップショット同期まで接続済み。開始種族は各 `playerId` の担当参加者自身が `種族.json` の選択肢から決定し、全担当勢力の選択が完了するまで準備完了・ゲーム開始できない。マルチプレイ開始時の `players[] / factionState` は空状態から生成し、`テストゲーム状態.json` のユニット・部隊・拠点を初期状態として使用しない。ホストが共有ワールドを生成して初期スナップショットを配信するところまで実装済みで、通信マルチ用の統治者作成・初期村配置フローと、ゲーム開始後の操作コマンド・ターン同期・差分同期は未実装。

---

## 3. 基本方針

初期実装は **ホスト権威型 + Socket.IOサーバー仲介型** とする。

```text
参加者A ─┐
参加者B ─┼─ Socket.IO Server ─ ホスト
参加者C ─┘                       │
                              ゲーム状態
```

Socket.IOサーバー:
- ルーム管理
- 接続管理
- プレイヤー識別
- コマンド受信順管理
- ホストへのコマンド転送
- 確定結果の配信
- 再接続管理

ホスト:
- ワールド状態の正本
- 移動判定
- 攻撃判定
- 乱数
- 敵AI
- ターン処理
- 地形イベント
- 経済処理

参加プレイヤーはゲーム状態を直接確定しない。

## 4. 既存ゲーム状態の再利用

マルチプレイ専用の別勢力状態を新規作成しない。

通信前のローカル複数勢力実装で、すでに参加者と勢力を分離した状態構造が導入されている。通信マルチプレイではこれをそのまま基盤として使用する。

```text
sessionParticipants[]
players[]
players[].controllerParticipantId
players[].factionState
activePlayerId
timeline.playerTurnOrder
timeline.activeTurnPlayerId
timeline.endedPlayerIds
```

`config/player_state_schema.json` の勢力プレイヤー構造:

```text
id
label
isPlayer
controllerParticipantId
race
ready
factionState
```

用語は次のように固定する。

- `participantId`: 実際の参加者・接続クライアントを識別するID。
- `playerId`: `players[].id` と同じ、ゲーム内の担当勢力ID。
- `controllerParticipantId`: その勢力を担当する参加者ID。
- `activePlayerId`: 現在画面へ表示している勢力ID。
- `activeTurnPlayerId`: 現在のローカル順番制で操作中の勢力ID。

現在のローカル順番制では `activePlayerId` と `activeTurnPlayerId` を揃えて1勢力ずつ操作する。通信マルチプレイでは全参加者が同じプレイヤーフェーズ中に同時操作するため、`activeTurnPlayerId` をサーバー側の操作権限判定には使用せず、`participantId -> assignedPlayerIds / controllerParticipantId` で担当勢力を検証する。

詳細は `ローカル複数勢力ターン設計.md` を参照する。

---

## 5. ホスト

ホストは「ルームを作った人」であると同時に、そのゲームのロジック確定権限を持つ。

ホスト専用権限:
- ゲーム開始
- ゲーム開始設定変更
- セーブデータ読込
- 必要に応じた参加者管理
- ゲーム終了

通常の移動・攻撃・建設・研究などはホスト自身も他プレイヤーと同じコマンド経路を通す。

ホストだけローカルで先に状態を変更しない。

---

## 6. 参加者識別

`socket.id` は再接続で変化するため、永続的な参加者IDとして使用しない。

最低限:

```text
participantId
connectionId(socket.id)
displayName
connected
ready
assignedPlayerIds
reconnectToken
```

を分離する。

`participantId + reconnectToken` により切断後も同じ参加者スロットへ戻れるようにする。

ゲーム内の `playerId` は勢力IDとして扱い、接続そのものの識別には流用しない。

---

## 7. ルーム状態

基本構造:

```text
Room
├─ roomId
├─ roomName
├─ phase
├─ hostParticipantId
├─ createdAt
├─ settings
│  ├─ factionCount
│  ├─ playerParticipantAssignments
│  ├─ playerFactionSelections
│  └─ gameSetup
├─ players
├─ chatLog
├─ commandSequence
├─ stateRevision
└─ game
```

`phase`:

- `lobby`: 参加待機・設定
- `setup`: ワールド生成・初期設定
- `playing`: 通常ゲーム
- `ended`: 終了済み

---

## 8. ルーム作成

クライアント:

```text
room:create
```

サーバー:
1. roomId生成
2. Room生成
3. participantId登録
4. hostParticipantId設定
5. Socket.IO roomへ参加
6. `room:created` を返す
7. `room:snapshot` を配信

`roomId` はサーバーが既存ルームと重複しない8桁の数字を自動発行し、作成画面では入力させない。作成者は表示用の `roomName` だけを入力する。参加時だけ「ルーム参加」を開き、共有された8桁の `roomId` を使用する。`playerName` はロビーの参加者一覧へ表示するプレイヤー名である。

---

## 9. ルーム参加

クライアント:

```text
room:join
```

確認項目:
- ルーム存在
- room.phase
- 人数上限
- ゲームバージョン
- participantId / reconnectToken
- 重複参加

成功後は `room:snapshot` を返す。

---

## 10. ロビーUI

v39では `v39-multiplayer-lobby.js` のロビーUIを使用する。旧 `RoomModal.vue` は簡易戦闘用UIとして維持する。

入室前はヘッダーに `ルーム作成 / ルーム参加` の2タブを表示し、選択した側の入力だけを表示する。ルーム作成側はプレイヤー名・ルーム名・作成ボタン、参加側はプレイヤー名・8桁ルームID・参加ボタンを表示する。入室後は2タブと作成/参加フォームを隠し、同じ画面をロビー専用表示へ切り替える。

ロビー表示:
- ルームID
- ホスト
- 参加プレイヤー一覧
- 接続状態
- 準備状態
- 担当勢力
- ゲーム開始設定
- ゲーム開始
- 退出 / ゲームから切断

ホストの `ゲーム開始` は、参加者一覧より下の設定領域へ埋め込まず、ロビー上部の主要操作列へ常時表示する。ゲーム開始設定未保存・未準備参加者あり・開始処理中の場合は同じ場所で無効化する。

ゲーム開始前は全参加者の準備状態を確認できるようにする。各担当勢力には開始種族の選択欄を表示し、その `playerId` を担当する参加者だけが変更できる。選択肢は `data/source/export/json/種族.json` を正本とし、通信コードへ種族一覧を重複定義しない。ゲーム開始後の `ゲームから切断` は参加者枠と `participantId + reconnectToken` を保持し、同じルームIDへ元参加者として再参加できるようにする。

---

## 11. 準備完了

各プレイヤー:

```text
room:ready
```

参加者は、自分が担当する全 `playerId` の開始種族を選択した後だけ準備完了にできる。

全人間プレイヤーが準備完了になるまで開始不可。

開始種族、担当参加者、ゲーム開始設定などゲーム開始に影響する内容が変更された場合は準備状態を解除する。

---

## 12. ゲーム開始

ホストのみ:

```text
game:start
```

サーバー確認:
- 送信者が hostParticipantId
- 全プレイヤー準備済み
- 設定値正常
- 勢力数上限内

ゲーム生成そのものは既存のゲーム開始・マップ生成処理を再利用する。

実装済み開始手順:

```text
各担当 playerId の開始種族を選択
↓
全員準備完了
↓
ホストが「ゲーム開始」
↓
server が host / ready / gameSetup / 担当勢力 / 開始種族を検証
↓
room.phase = setup
↓
ホストへ game:start:host
↓
startV39MultiplayerSession()
  └─ テスト状態を複製せず、空の players[] / factionState を生成
↓
既存 generateFieldFromSettings()
↓
既存 v39 セーブ形式で初期スナップショット作成
↓
server が検証して room.phase = playing
↓
参加者へ game:snapshot
```

開始種族は `players[].race` へ入り、担当者は既存の `players[].controllerParticipantId` を使用する。マルチプレイ用の別マップ生成処理は作らない。

現時点ではワールド生成直後に `playing` へ進むが、次段階では `setup` を維持したまま既存の統治者作成・初期村配置を通信対応し、全勢力の初期配置完了後に `playing` へ移す。

---

## 13. 初期設定・初期村配置

マルチプレイの新規ゲームでは `テストゲーム状態.json` を初期キャラクター・部隊・拠点の供給元にしない。

目標の初期セットアップ順は次の通り。

```text
ロビーで開始種族を選択
↓
共有ワールド生成
↓
各プレイヤーが選択済み種族で統治者を作成
  └─ 既存のクラス選択・名前決定・キャラクター生成ルールを再利用
↓
各プレイヤーが初期村を配置
  └─ 既存の初期村配置条件・領土作成・初期人口/資源計算を再利用
↓
全担当勢力の初期配置完了
↓
敵・一般村などの初期生成を1回だけ実行
↓
通常プレイ開始
```

開始種族選択と空の勢力状態生成までは実装済み。また、統治者が存在しない勢力では既存の初期村配置が自動開始しないよう停止済み。通信マルチでの統治者作成、初期村配置の操作同期、全員完了集約は未実装。

各参加者は自分の担当 `players[].factionState` のみ操作する。

初期村配置など、同じ対象への操作が競合する場合はサーバー受信順を確定順とする。

先着命令を確定後、後着命令を更新済み状態で再判定する。

---

## 14. ゲーム中のコマンド

参加クライアントは「結果」ではなく「操作要求」を送る。

例:

```text
Player2
  ↓
game:command
  ↓
Socket.IO Server
  ↓
serverCommandSeq付与
  ↓
Host
  ↓
既存ゲーム処理
  ↓
game:commit
  ↓
Socket.IO Server
  ↓
全参加者
```

悪い例:

```text
unit1を x=10,y=20 に移動済みにする
```

良い例:

```text
unit1を x=10,y=20 へ移動したい
```

---

## 15. コマンドEnvelope

```json
{
  "roomId": "12345678",
  "participantId": "participant-1",
  "playerId": "player-1",
  "clientSeq": 18,
  "targetRound": 12,
  "targetPhase": "player",
  "type": "unit:move",
  "payload": {}
}
```

サーバーは受信後 `serverCommandSeq` を付与し、その順番でホストへ処理させる。

---

## 16. 重複実行防止

参加者ごとに `lastClientSeq` を保持する。

同じ `participantId + clientSeq` は再実行しない。

再送・再接続が発生しても同じ操作が二重適用されない構造にする。

---

## 17. stateRevision

確定ゲーム状態へ `stateRevision` を持たせる。

正式な状態変更ごとに増加する。

クライアントとホストの revision が一致しない場合、差分再取得またはフルスナップショット再取得を行う。

---

## 18. 状態同期

ゲーム開始時は既存v39セーブ形式をそのまま利用したフルスナップショットを送る。サーバーは初期スナップショットをメモリ上へ保持し、ゲーム開始後に同じ参加者が再接続した場合は再送する。通信切断だけでなく、ゲーム中に明示的に `ゲームから切断` した場合も参加者枠と再接続情報を削除せず、同じ `participantId + reconnectToken` で再参加した時に同じスナップショットへ復帰させる。

通常操作では巨大なワールド状態全体を毎回送らず、今後のStage 4で変更イベント・差分を配信する。

フルスナップショットを使用する場面:
- ゲーム開始（実装済み）
- 再接続（サーバー保持中の最新スナップショット再送まで実装済み）
- 同期エラー
- セーブ復元
- ホスト変更

新規の途中参加は現時点ではゲーム開始後に拒否する。途中参加を許可する場合は、担当勢力とFog公開範囲を含めて別途接続する。

既存JSONセーブ・v39状態をベースにし、通信専用の第二正本を作らない。

UIローカル状態（開いているモーダル、マウス位置、カメラドラッグ中など）は共有しない。

---

## 19. Fog of War

ホストは全ワールド状態を保持する。

参加者へ送る情報は各プレイヤーの visibility と整合させる。

将来的には:

```text
共通公開状態
+
プレイヤー別公開状態
```

へ分離する。

敵の完全位置など未発見情報を参加クライアントへ送信するかは実装前に確定する。

開発初期に全状態送信を採用する場合は暫定実装として明記する。

---

## 20. ターン処理

既存の正式3フェーズを使用する。

```text
プレイヤーターン
  ↓
エネミーターン
  ↓
全体終了処理
```

マルチプレイでは人間プレイヤーごとの順番を設けず、同じプレイヤーターン中に同時操作する。

---

## 21. ターン終了

各プレイヤー:

```text
turn:end
```

ターン終了したプレイヤーはそのターン中の通常操作を停止する。

全員終了前なら:

```text
turn:cancel-end
```

で取消可能。

全人間プレイヤーが終了したら、ホストだけがエネミーターンと全体終了処理を実行する。

---

## 22. 乱数

以下はホストだけが確定する。

- 命中
- ダメージ乱数
- 敵AI対象選択
- 敵AIスキル選択
- 災害
- 噴火
- イベント

参加クライアントは確定結果だけを受け取る。

---

## 23. 切断・再接続

切断時にプレイヤーゲーム状態を削除しない。

```text
connected = false
```

へ変更する。

同じ `participantId + reconnectToken` で戻った場合、元の参加者スロットへ復帰する。

切断・放置時の自動ターン終了はゲーム設定で ON/OFF を持つ。

OFF では期限なく待機可能とする。

ON 時の待機時間・判定条件は別途確定する。

---

## 24. ホスト切断

最終的にはホスト移譲に対応する。

基本候補は「参加順が最も早い接続中プレイヤー」。

```text
room:host-changed
```

で通知する。

ただし初期MVPではホスト移譲よりも、ルーム作成・参加・ゲーム開始・基本同期を優先する。

---

## 25. セーブ

マルチプレイ中のセーブはホストが行う。

既存JSONセーブ形式を拡張し、最低限以下を保持する。

- ルーム設定
- players
- 担当勢力
- ワールド状態
- ターン状態
- プレイヤー別状態
- 敵状態
- 研究
- 領土
- 拠点
- 外交
- Fog

ルームID自体は復元必須としない。

将来的に「新規ゲーム / セーブからルーム作成」を選択可能にする。

---

## 26. 退出

ロビー退出:
- 即時退出可能

ゲーム中退出:
- プレイヤーの勢力・ゲーム状態は削除しない
- `connected=false` とする

## 27. Socket.IOイベント案

### Client → Server

| Event | 用途 |
|---|---|
| `room:create` | ルーム作成 |
| `room:join` | 参加 |
| `room:leave` | 退出 |
| `room:ready` | 準備状態変更 |
| `room:select-faction` | 担当 playerId の開始種族選択 |
| `room:update-settings` | ホスト設定変更 |
| `room:chat:send` | チャット |
| `game:start` | ゲーム開始 |
| `game:command` | ゲーム操作 |
| `game:commit` | ホストによる操作確定 |
| `game:snapshot` | ホストの状態提出 |
| `turn:end` | ターン終了 |
| `turn:cancel-end` | 終了取消 |

### Server → Client

| Event | 用途 |
|---|---|
| `room:created` | 作成成功 |
| `room:snapshot` | ロビー全状態 |
| `room:error` | エラー |
| `room:host-changed` | ホスト変更 |
| `room:chat` | チャット更新 |
| `game:starting` | ホスト生成中を全員へ通知 |
| `game:start:host` | ホストへ開始要求 |
| `game:started` | 初期同期完了・playing移行 |
| `game:start-failed` | 開始失敗 |
| `game:command:host` | ホストへ操作命令 |
| `game:event` | 確定イベント |
| `game:snapshot` | 完全同期 |
| `game:command-rejected` | 命令拒否 |

既存イベントとの重複は実装時に整理する。

---

## 28. 不正操作対策

サーバーで最低限確認する。

- ルーム所属
- participantId
- playerId
- participantId がその playerId を担当しているか
- 現在phase
- ターン終了済みか
- clientSeq重複
- アプリ/通信バージョン

移動距離・射程・AP・建設条件などゲームルールの最終判定は既存ゲームロジックを使用する。

クライアント申告のダメージ量・移動結果・取得資源量などは信用しない。

## 29. UI導線

ゲーム開始前:

```text
[シングルプレイ] / [マルチプレイ]
  ├─ シングルプレイ → ゲーム開始設定 → ローカル生成
  └─ マルチプレイ → [ルーム作成 | ルーム参加] の2タブ
                         ↓

                         ↓
                  担当勢力の開始種族を各自選択
                         ↓
                 ホストのみゲーム開始設定を共有保存
                         ↓
                     全員準備完了
                         ↓
                    ホストがゲーム開始
                         ↓

                         ↓
```

参加者はロビーで共有設定を確認するだけで変更できない。設定保存後はロビーへ戻り、全員準備完了後にホストだけが開始できる。

ゲーム開始後もルーム情報確認用の入口は残す。

## 30. GitHubと実行サーバー

GitHubはコード・仕様の正本であり、Socket.IOルームを実行するサーバーではない。

実運用構成:

```text
GitHub
  ↓
Node.jsアプリを配置
  ↓
server.js
  ↓
Express + Socket.IO
  ↓
参加プレイヤー
```

全参加者は同じNode.jsサーバーURLへアクセスする。

GitHub Pagesのような静的ファイル配信だけでは現行 `server.js` / Socket.IO は動作しない。

## 34. 最重要原則

マルチプレイ化のために現在のゲームロジックを別物として作り直さない。

既存の:
- 移動
- 戦闘
- 建設
- 研究
- ターン処理
- 敵AI
- ゲーム状態

をホストが利用する。

通信層は原則として、

```text
操作要求を届ける
処理順を決める
確定結果を届ける
```

ことに専念する。

シングルプレイとマルチプレイでゲームルールが分岐しない構造を目標とする。
