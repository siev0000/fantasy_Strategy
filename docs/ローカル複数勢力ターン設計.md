# ローカル複数勢力ターン設計

最終整理: 2026-09-24

## 1. 目的と対象外

- 通信マルチプレイへ接続できる状態構造を、通信なしで先に検証する。
- 1台の端末で、1人以上のローカル参加者が担当勢力を順番に操作できるようにする。
- 開始設定で勢力数を決め、ローカル参加者へ勢力を割り当てる。
- 本設計ではネットワーク接続、ルーム作成、外部参加、同期、再接続、ホスト移譲は実装しない。

## 2. 用語

- **勢力**: マップ上で都市、領土、ユニット、Fog、研究などを所有する `players[]` の1要素。
- **参加者**: 操作を行う人または将来の接続クライアント。勢力とは別IDで管理する。
- **担当勢力**: 参加者が操作できる勢力。1参加者は複数勢力を担当できる。
- **ローカル順番制**: 1台の端末で担当勢力を1つずつ切り替えて操作する本実装の進行方式。

## 3. 正本データ

ゲーム状態の勢力本体は既存どおり `players[]` と各 `players[].factionState` を正本とする。
ユニットや都市を参加者へ複製しない。

```js
{
  sessionParticipants: [
    {
      participantId: "local-1",
      name: "参加者1",
      controlMode: "local",
      assignedPlayerIds: ["player-1", "player-2"]
    }
  ],
  players: [
    { id: "player-1", controllerParticipantId: "local-1", factionState: {} },
    { id: "player-2", controllerParticipantId: "local-1", factionState: {} }
  ],
  timeline: {
    phase: "player",
    playerTurnOrder: ["player-1", "player-2"],
    activeTurnPlayerId: "player-1",
    endedPlayerIds: []
  }
}
```

- `activePlayerId` は画面の表示・選択対象を示す既存値として残す。
- ローカル順番制では `activePlayerId` と `activeTurnPlayerId` を同じ勢力にする。
- `controllerParticipantId` と `assignedPlayerIds` は正規化して一致させる。片方だけを更新する実装は作らない。
- セーブには参加者、担当勢力、ターン順、終了済み勢力を含める。旧セーブでは `local-1` が既存全勢力を担当するよう移行する。

## 4. ゲーム開始

1. 開始設定で勢力数を選ぶ。
2. 同数の `players[]` を生成する。
3. ローカル参加者を1人以上、勢力数以下で作る。開始設定では通信前の仮参加者として扱う。
4. 参加者ごとに担当勢力を割り当てる。各勢力の担当は必ず1人とし、1参加者は複数勢力を担当できる。
5. 全勢力の初期拠点配置を完了してから、敵・一般村などのワールド初期生成を始める。

参加者数と勢力数は別である。参加者1人・勢力3でも有効とし、その参加者が3勢力を順番に操作する。

## 5. ローカル順番制のターン遷移

1. `phase=player` の間、`activeTurnPlayerId` の勢力だけが操作できる。
2. ターン終了時、その勢力IDを `endedPlayerIds` へ追加して操作を停止する。
3. 未終了の次勢力があれば、`playerTurnOrder` 順で `activeTurnPlayerId` と `activePlayerId` を切り替える。
4. 全勢力が終了したら、既存のエネミーターン、全体終了処理を1回だけ実行する。
5. 次ラウンドでは `endedPlayerIds` を空にし、`playerTurnOrder` の先頭勢力から開始する。

同じ勢力が同一ラウンドで2回終了できない。終了済み勢力は、エネミーターン開始前でもローカル順番制では再操作・終了取消をしない。

## 6. 将来の通信マルチプレイへの接続

- 将来のネットワーク方式では、参加者IDを接続IDへ対応付けるが、勢力IDと勢力データの形式は変えない。
- 通信時は同じ `endedPlayerIds` を使い、全参加者が同時に操作する。`activeTurnPlayerId` はローカル画面の表示用に限定し、サーバー正本の操作可否には使わない。
- クライアントは `participantId`、`playerId`、ターン番号、連番を含む命令をホストへ送る。ホストが担当・フェーズ・AP・対象を検証してから状態を確定する。
- 本実装では命令送信や通信待機を模擬しない。ローカル処理は同じ検証関数を直接呼び出す。

## 7. 検証条件

- 参加者1人・勢力1で、従来どおりターン終了後にエネミーターンへ進む。
- 参加者1人または複数人・勢力2以上で、ターン終了後に次勢力へ切り替わり、全勢力終了後だけエネミーターンへ進む。
- 各勢力のユニット、都市、Fog、研究、ログが他勢力へ混ざらない。
- 初期拠点を全勢力分配置するまで敵・一般村を生成しない。
- セーブ/ロード後も参加者の担当勢力、現在操作勢力、終了済み勢力、次のターン順が一致する。
