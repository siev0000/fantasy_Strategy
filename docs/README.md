# ドキュメント案内 / 仕様書の優先順位

最終整理: 2026-09-24

このディレクトリには、現行仕様・実装ルール・将来設計・過去メモが混在している。
今後はこのファイルを入口とし、下記の優先順位で参照する。

## 1. 仕様判断の優先順位

仕様が食い違う場合は、原則として次の順で判断する。

1. **現行コード / `data` / `config` の実データ**
2. **`現状ゲーム仕様メモ.md`** — 現在動いているゲーム全体の仕様まとめ
3. **個別の現行ルール資料** — キャラ、地形、マップなど
4. **`ALL_TASKS_UNIFIED.md`** — 今後の実装ロードマップ
5. **将来設計メモ** — 未実装案を含む
6. **旧タスク・旧草案・履歴** — 仕様確定の根拠には使わない

> 注意: `仮` / `暫定` / `将来` / `未実装` と書かれた内容は、現行コードに存在することを意味しない。

## 5. `progress.md` の扱い

ルート直下の `progress.md` は**開発履歴**として残す。

- 実装時期や変更経緯を調べるときに使う。
- 現在の仕様を判断するときの正本にはしない。
- 履歴と現行コードが食い違う場合は現行コードを優先する。

---

## 6. 今後のドキュメント運用

- 新しく確定した現行仕様は、まず `現状ゲーム仕様メモ.md` または対応する個別ルールへ反映する。
- 未実装案は現行仕様へ混ぜず、設計資料または `ALL_TASKS_UNIFIED.md` のバックログへ入れる。
- 完了したタスクはロードマップから状態を更新する。
- 同じ内容の仕様書をルート直下と `docs/` に二重配置しない。
- `progress.md` には変更履歴を残してよいが、仕様本文の代わりにはしない。

### 6-1. 未確定箇所の仮実装

- 通信マルチプレイ以外は、未確定箇所が残っていてもゲームループ全体を最後まで一通り動かせる状態を優先する。
- 未確定の数値・確率・補正は仮値を設定し、未確定であることだけを理由に処理を未接続のまま残さない。
- 未確定の分岐仕様は、既存ルールと矛盾しない最小構成で仮実装する。
- 仮値と仮分岐はJSONまたは共通設定へ集約し、処理内へ同じ値を重複して直書きしない。
- 仮実装には `暫定` と調整対象を明記し、後から設定・データまたは共通関数の変更だけで差し替えられる形にする。
- 仮実装でもセーブ・ロード、ターン進行、敵味方共通処理を途中で切らず、開始から結果反映まで接続する。
- バランス調整、演出追加、詳細ルールの再確定は、基本ループが一通り動いた後の調整タスクとして管理する。
