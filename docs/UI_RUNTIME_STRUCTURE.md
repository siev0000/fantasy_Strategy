# UI実行経路と負荷の整理

更新: 2026-10-15

2026-10-16 UI構成更新: `GAME_UI_LAYOUT_RULES.md` を共通契約に追加。自キャラの部隊タブも同じユニットカードと詳細描画を呼ぶ。フィールド下部の交流は `v39-operation-ui.js` が枠を所有し、既存 `v39-world-population.js` の接触操作を置く。村モーダルでは同じ接触操作を選択肢領域へ移し、閉じると交流へ戻す。発言は別領域で保持する。拠点の取引入口は既存toolbar内へ配置し、後付けボタンでパネルのグリッド行数を増やさない。

新機能の追加前に、同じUIを描画する実行経路と更新の責任を確認する。ファイルの数だけで負荷や二重実行を断定しない。

## 今回修正した負荷

- 部隊の1回の描画中に、検索のたびに `getV39ActiveFactionState()` から複製を取得していた。描画開始時の1つのスナップショットを共有し、描画終了後は保持しない。
- 同じ内容でも部隊選択・一覧・装備・スキルを毎回 `innerHTML` で再作成していた。出力内容が変わった場合だけ置換する。値変更時の更新は継続し、変わらないカードのDOMとフォーカスを維持する。
- 完成済みの共通カードに旧ゲージ変換を適用する互換処理を削除した。CSSはカードの共通描画から読み込み、後付けstyle要素の注入を廃止した。
- 名前・座標の文字幅は、同じDOM・幅・文字・フォント条件なら再計測しない。リセット/計測/反映をまとめ、1文字列ずつのスタイル変更とレイアウト読取の往復を避ける。画面幅・表示設定・フォント読込で再計測する。
- 道具欄のdocument全体クリック購読を削除。存在しない `squad-derived-updated` ではなく、実際に発行される `squad-detail-rendered` を購読する。

## 計測・検証

`scripts/check-v39-ui-render-work.mjs` は専用地上フィクスチャで同じ部隊UIを10回明示更新する。390/1100pxで修正前は各領域を10回置換、文字幅用style書込132回、同期処理約187ms。修正後は対象4領域の置換0回、文字幅用style書込0回、約47〜53msだった。これは特定の更新処理の測定であり、全ゲームのFPS・ターン時間・メモリが同じ比率で改善したという意味ではない。

```powershell
npm run check:ui-render-work
```

出力は `output/web-game/ui-render-work`。タイミングは環境で変動するため固定msの合否判定にしない。変更なしでのDOM同一性、無関係クリック時の道具欄不更新、実際の名前/HP更新、行動・モーダルのスキル表示を検証する。

- `v39-cave-world.js` の鉱床担当欄は軍隊/搬入先のselectとoptionを再利用する。候補の削除は反映し、別所有者/別階層の選択は引き継がない。休息地点カードの保持は前工程で実装済み。
- 専用確認は `npm run check:trade-input-stability`、既存物資取引は `check-v39-trade-baskets.mjs`、実輸送/警備/保存は `check-v39-expedition-test-fixture.mjs`。UI更新保持の確認であり、ターン全体の性能解決とはしない。

1. エフェクト設定は下記の再生統合まで完了。カテゴリ初回UI組み立てやUI状態復元は役割別モジュールとして残る。これらの整理が必要でも、再び別の再生状態やDOM監視を追加しない。
2. 道具の補充/群生地採取/荷下ろしは下記の読み取り専用判定へ移行済み。他の可否表示で実行関数を呼んでいないかは引き続き確認する。
3. 資源ヘッダーと自キャラモーダルは下記の保持更新へ移行済み。残る洞窟の行動欄なども元の所有者内で整理する。

これらは今回すべて解消した項目ではない。特にエフェクト設定の分散を、この計測だけでゲーム全体の重さの主因と断定しない。

## エフェクト設定の統合（2026-10-15）

- `v39-effect-settings-loop-controls.js` と `v39-effect-gradient-motion-mode.js` を削除。下側再生ボタン、移動方式、元画像全体の選択肢を元の画面で最初から描く。
- ループ実行状態・再生/停止・コマ表示・静止画への復帰を `v39-effect-settings.js` で管理する。ボタンの代理クリック、停止のための再生方式の往復変更、別ファイルによる固定時間の復帰タイマーを廃止。停止/閉じた後は古い非同期読込の完了で再生しない。
- `PhaserEffectPlayer.prototype.play` の実行時書き換えを削除。グラデーション移動方式は通常の再生引数として渡す。
- 保存/読込/初期化は登録した編集対象ハンドラーを元の画面から呼ぶ。タイトルへの戻りも閉じた後のコールバックで処理する。クリックの捕捉と `stopImmediatePropagation()` で元の処理を無効化しない。
- 静止描画モジュールは描画関数のみとし、コントロール追加・パネル属性のMutationObserver・イベント購読を持たせない。カテゴリ側のbody監視と、UI状態復元側の初期化ポーリングも外し、カテゴリ初期化後に復元処理を呼ぶ。
- プレビュー用Phaserは静止・コマ停止・閉じた状態で休止し、必要な描画/再生時だけ起動する。通常フィールドのゲームループは変更しない。
- 保存したコマ番号は画面を開くまで値だけ保持する。非表示画面の復元のためにPhaserを初期化せず、コマ数が判明するまでタイマーで待つ処理も使わない。表示後に範囲へ収め、実際のコマを描く。

専用確認は `npm run check:effect-editor-lifecycle`。390/1100pxで、静止/停止/閉じた後のプレビューCanvas描画呼出し0回、明示再生、ループ中の対象変更、元画像、グラデーション移動方式、設定/コマ位置のロード、タイトル/管理への戻りを確認。これは静止中のプレビュー負荷の検証であり、大マップ全体の性能測定ではない。

関連テストで既存の不整合も判明した。`check-v39-effect-attack-means.mjs` はスキルにある「弓」がカテゴリ設定にないため先頭のデータ網羅確認で失敗する。`check-v39-auto-combat-effects.mjs` はdata URLで読み込んだソースの相対依存 `v39-defense-rules.js` を解決できず、ブラウザ確認前に失敗する。今回のUI統合ではこのデータ/旧テスト方式を変更していない。成功した画面テストと区別し、後続で直す。

## 道具判定・資源ヘッダーの整理（2026-10-15）

- `v39-expedition-tools.js` 内に補充/群生地採取/荷下ろしの読み取り専用 `inspect` を置き、実行関数も同じ判定から処理する。UI表示のために実行関数を呼び、更新後のplayers/units/settlements/mapを作って捨てる経路を削除した。別ファイルに条件を複製しない。
- 道具欄は同じIDのカードを再利用し、タイトル/説明/開閉状態が変わった場合だけ更新する。実行先のコールバックは毎回更新し、見た目が同じでも古い対象を呼ばない。無くなった行だけ削除し、追加/並び替えも元のリスト内で行う。
- 資源ヘッダーは1回の更新で資源スナップショットを1回だけ取得し、通常3分類と特殊資源で共用する。通常の取得経路もワールド状態全体ではなく操作プレイヤーの選択拠点から作る。拠点の正規化と数値の丸め規則は維持する。
- ボタンとイベント登録は再利用し、数値が変わったときだけ表示値を更新する。特産品パネルも同じ内容なら置換せず、選択タブとフォーカスを保持する。閉じているヘッダーの所有者確認はスカラーのプレイヤーIDだけ取得し、状態全体を複製しない。
- 同じヘッダー10回の更新を390/1100pxで計測。整理前は資源取得80回/ワールド状態取得90回/ボタン再生成あり/約55ms。整理後は資源取得10回/ワールド状態取得0回/変更なしのHTML書込0回/約5〜7ms。プレイヤーの複製や拠点の正規化まで0になったわけではない。大マップ全体の改善率ではない。

`check-v39-ui-render-work.mjs` にヘッダーの取得回数・DOM/フォーカス保持・実在庫変更・内訳/特産品タブの検証を追加した。`check-v39-expedition-test-fixture.mjs` は開発版で凍結した入力への判定/実行、枯渇・拒否理由の一致を確認し、配信用ビルドでは実道具操作・カード保持・輸送・侵入・保存を確認する。取引の元ヘッダーは `check-v39-trade-baskets.mjs` で320/390/1100pxを確認する。

## 自キャラモーダル・マップ更新（2026-10-15）

- `v39-character-modal.js` 自身で枠・タブ・一覧を保持し、カードをIDで再利用する。詳細も同じ出力なら置換しない。状態通知はフレーム内でまとめ、直接の操作更新は即時に反映する。共有の能力/スキル/装備描画は維持する。
- 同一対象の更新ではスクロール、能力セクションの開閉、装備タブの未保存道具設定と入力フォーカスを保持する。在庫の表示値は更新する。対象プレイヤー/ユニット/タブを変えた場合は入力を引き継がず、保存成功時は確定値へ同期する。
- 390/1100pxで変更なしの10回更新を測定。整理前はモーダル全体を10回置換しフォーカス消失、約11〜15ms。整理後は子要素の置換0回、一覧/詳細/フォーカス保持、約7〜8ms。装備編集中の在庫変化、HP更新、能力更新時の閉じたセクションも回帰対象とした。
- `v39-map-entities.js` は描画開始時のスナップショットから自軍・他軍・ワールドIDを共用し、ユニットごとの状態取得を廃止。索敵描画と成長タブも不要な保存ワールドを取得しない。洞窟の行動表示・休息表示・採取可否も同様とし、ワールド切替/鉱床/保存の取得は維持する。
- 特産品は既存のユニットレイヤーに置くまま、再描画前に一時的に取り外して再利用する。アイコン/発見状態/占有状態が変わったマスだけ作り直し、消えたものは破棄する。地上から洞窟へ移ると古い特産品も破棄する。別レイヤーや後付け置換処理は追加しない。

### マップの計測条件

`npm run check:map-snapshot-work` は実生成100×100、初期拠点配置後、自軍40体＋別ワールド1体、保存済み地上/14×14洞窟で測定する。ランダム敵は描画計測前に除去し、特産品1,194個をテスト表示する。HPを毎回変更し、単なる変更なしスキップではない描画を3回測る。

- 初期配置前の予備計測で、マーカー描画1回の状態取得43回を確認。整理後は配置後の大マップでも洞窟でも1回、保存ワールド取得0回、別の自軍スナップショット取得0回。
- 初期配置後の特産品再作成が残った状態では約208〜226ms。再利用後は約25〜30ms（うち状態取得は約15〜18ms）。1,194個の同一性、対象ワールドの味方40体/1体の描画、索敵描画の保存ワールド取得0回を検証する。
- 14×14洞窟の同じ更新は約2〜3ms。上記は特定の描画処理であり、FPS、生成時間、全ターンの改善率ではない。時間は合否に使わず、取得回数とオブジェクト再利用を回帰条件にする。
- 出力は `output/web-game/map-snapshot-work`。JSONに状態取得内訳を、`.cpuprofile` に描画区間のCPU記録を出す。特産品の通常時非表示/テスト時半透明、発見後表示、占有時の右上配置/移動後の中央復帰は `check-v39-specialties.mjs` でも確認する。

実ターンは `V39_PROFILE_TURN=1` を追加すると、地上と洞窟で各1ターン進め、呼出元別の取得回数/複製時間と既存ステージ計測を記録する。初回は約11〜12秒、保存ワールド取得100〜151回だった。洞窟UI整理後は90〜109回。今回さらに以下を整理した。

- ターン表示はtimelineだけを取得する。勝利地形/災害/継承判定/調査表示/近接発見/修復可否/村テスト表示/会話表示は不要な保存階層を取得しない。
- 研究による発見は、軽量な入力署名が変わった時だけ保存階層も取得する。通常の表示更新で保存済み洞窟を複製せず、研究完了時の非表示階層への発見反映は維持する。
- ワールドコンテキストの内部更新で戻り値を読まない箇所だけ `returnState:false` を渡す。通常の `setV39GameState` は従来どおり複製済みの状態を返す。データを書かない/生状態を返す高速化ではない。
- 非表示ワールドのプレイヤー取得で、自軍を別getterから二重複製していた経路も1回の取得へ統合した。コンテキスト外に変更可能なスナップショットを保持しない。

| 同じ試験の計測 | 地上表示 | 洞窟表示 |
| --- | --- | --- |
| 着手前 | 約11.3秒 / 公開getterの保存階層取得90回 | 約10.2秒 / 109回 |
| 読取整理後 | 約9.5秒 / 43回 | 約9.1秒 / 48回 |
| 未使用の戻り値も省略後 | 約9.1秒 / 43回 | 約8.3秒 / 48回 |

公開getter内で測った複製時間は地上約4.5→3.1秒、洞窟約4.1→2.7秒。これはsetterの戻り値や他の内部コピーをすべて数えた値ではない。背景の地上敵も進行し、敵数・生成・演出待ちでも変動するため、洞窟だけのAI時間や全体FPSの改善率にはしない。結果は `output/web-game/map-snapshot-work/current-turn-before.json` / `final-turn-after.json`。全体の重さは残る。

`check-v39-turn-snapshot-safety.mjs` は通常/戻り値省略の書込、現行の統合調査Lvでの研究完了→地上/保存洞窟の発見、他プレイヤー分離、別の保存洞窟の保持、セーブ復元を確認する。旧研究UIテストの仕様不整合と区別する。

会話と取引は `v39-trade-layout.js` の1つの管理処理で元の資源ヘッダーを保持する。モーダルごとの別ヘッダーや別の監視による奪い合いは作らない。修正状況一覧は `UI_FIX_QUEUE.md`。

## 今後の変更ルール

- UIを変更するときは、最初に描画元・呼出元・状態の所有者を確認する。描画後に別モジュールで似たHTMLへ置換する実装を追加しない。
- 既存の共通描画・更新処理へ統合し、置換前の経路を残したまま新しい経路を恒常的に重ねない。
- MutationObserverはDOM構造が外部から変わる必要がある箇所だけに限定する。利用する場合も、同じ内容を再書込しない。通常の更新には所有者からの明示的な通知を優先する。
- document全体のクリックで全パネルを再構築しない。該当操作・該当状態の変更だけを購読する。
- 大きな整理は機能単位で行い、既存テスト・実画面・保存復元を確認してから次へ進む。
