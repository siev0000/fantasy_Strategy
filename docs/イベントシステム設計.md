# イベントシステム設計

> 状態: 一部実装 / 設計中（編集書式は2026-10-14確定）
>
> 目的: 一般村依頼を最初の利用対象として、イベント内容をデータ追加だけで増やせる共通イベント基盤を設計する。
>
> 実装済み範囲は `一般村イベント共通ルール.md` を参照する。本書21節の編集書式は採用済みだが、番号付きセルの変換・会話分岐は未実装。他の設計案も、現行コードで確認できない限り現行挙動として扱わない。

---

## 1. 基本方針

- イベントごとの固有処理をJSへ追加する方式にはしない。
- ランタイムはイベント定義JSONを読み、共通の条件判定・進行管理・結果適用を行う。
- 新規イベントが既存の条件タイプ・進行形式・効果タイプだけで表現できる場合、JS修正なしで追加できることを目標とする。
- 新しい仕組みが必要な場合だけ、共通の「進行形式」または「効果タイプ」を1つ追加する。
- 種族名、イベント名、報酬量、必要数などをコードへ固定定義しない。
- セーブデータにはイベント定義そのものを複製せず、イベントIDと進行状況だけを保持する。
- 最初の対象は一般村イベントとするが、将来は探索、都市、外交、国家、災害等でも同じエンジンを利用できる構造にする。

---

## 2. ファイル分割方針

イベントは全件を1ファイルへ集約せず、**ゲームシステム単位**で分ける。

初期候補:

- `イベント_一般村.json`
- `イベント_探索.json`
- `イベント_都市.json`
- `イベント_外交.json`
- `イベント_国家.json`

種族ごとのファイル分割は行わない。

理由:
- 共通イベントや複数種族対象イベントの置き場所が曖昧にならない。
- 「一般村イベントを全部確認する」ときに複数ファイルを横断しなくてよい。
- 種族差は発生条件として定義できる。

報酬も原則イベント定義内に持つ。

同じランダム報酬セットを多数のイベントが共有する必要が生じた場合のみ、将来 `報酬テーブル.json` の追加を検討する。

## 3. 「イベント種別」と「進行形式」を分離する

### 3-1. イベント種別

イベントがゲーム上で何を意味するかを表す。

初期候補:

- `依頼`
- `救援`
- `契約`
- `交流`
- `支配`
- `ランダム`

これは主に、
- UI表示
- イベント一覧の分類
- 発生タイミング
- AIや村側の提示方法

に使う。

### 3-2. 進行形式

イベントを**どう進め、何をもって完了とするか**を決める。

初期候補:

| 進行形式 | 用途 | 例 |
|---|---|---|
| `即時` | 選択した時点で結果を適用 | 契約を結ぶ、援助を断る |
| `納品` | 指定資源・装備等を渡す | 食料50を届ける |
| `討伐` | 指定対象を指定数倒す | マンティコア1体討伐 |
| `探索` | 指定地点・地形・対象を調査する | 鉱脈調査、遺跡探索 |
| `到達` | 指定地点へユニットが到達する | 村人の捜索地点へ向かう |
| `護衛` | 対象を目的地まで生存させる | 貢物護送、避難民護衛 |
| `防衛` | 指定対象を一定条件まで守る | 村への襲撃を撃退 |
| `判定` | 指定技能等で判定する | 仲裁、威圧、浄化 |
| `作業` | 指定地点でAP・ターン・資源等を使って作業する | 橋修理、巨岩撤去 |
| `建設支援` | プレイヤー技術で一般村へ施設を建設する | 防壁、城壁、見張り塔 |
| `複合` | 複数目標を組み合わせる | 救出地点へ到達→敵討伐→村へ帰還 |

重要:
- 種族やイベント固有名で処理を分けない。
- `進行形式` に対応する共通ハンドラーで処理する。
- `複合` は専用イベント処理を書かず、既存の目標タイプを複数並べて処理する。

## 4. 一般村イベントでの例

### 人間: 街道の安全確保

- イベント種別: `依頼`
- 進行形式: `討伐`
- プレイヤー種族条件: 人間
- 目標: 指定された敵を倒す
- 完了結果: 一般村友好度上昇 + 報酬

### 人間: 不足物資の援助

- イベント種別: `依頼`
- 進行形式: `納品`
- プレイヤー種族条件: 人間
- 目標: 指定資源を村へ渡す
- 完了結果: 一般村友好度上昇

### 悪魔: 生贄の契約

- イベント種別: `契約`
- 進行形式: `即時`
- プレイヤー種族条件: 悪魔
- 友好度等の発生条件を満たした場合のみ提示
- 選択結果として人口、魂、友好度、契約状態等を変更可能にする

### 竜人: 貢物の護送

- イベント種別: `依頼`
- 進行形式: `護衛`
- 村から護送対象を生成または参照
- 指定地点まで生存させると完了

### 人間: 村人の救出

単純な1形式で表現できない場合は `複合` とする。

例:
1. 救出地点へ `到達`
2. 周辺の敵を `討伐`
3. 生存者を村まで `護衛`

## 6. 条件を3種類に分ける

条件は用途を混在させない。

### 6-1. 発生条件

イベント自体を候補に入れる条件。

例:
- プレイヤー種族
- 村種族
- 一般村友好度
- 一般村人口
- 属国状態
- 地形
- 研究Lv
- 資源量
- 周辺の敵存在
- 過去イベント完了
- ターン数

### 6-2. 選択条件

イベントは表示されているが、その選択肢を使用できるかを決める条件。

例:
- 穀物50以上を所持
- 交渉50以上
- 特定スキルを所持
- 友好度80以上

満たしていない選択肢を非表示にするか、無効表示にするかはUI設計時に確定する。

### 6-3. 達成条件 / 目標

受諾後に何を完了すればよいかを表す。

例:
- 対象敵を3体討伐
- 指定資源を50納品
- 指定マスへ到達
- 3ターン防衛
- NPCを目的地へ護衛

## 7. 効果タイプ

イベントの結果は共通の効果ハンドラーで処理する。

初期候補:

- `一般村友好度変更`
- `一般村人口変更`
- `プレイヤー資源変更`
- `一般村資源変更`
- `研究EXP変更`
- `敵生成`
- `放浪者生成`
- `ユニット生成`
- `状態追加`
- `契約追加`
- `属国化`
- `直接支配`
- `イベント開始`

イベント固有のJS関数名をJSONへ直接書かず、登録済みの効果タイプから選ぶことを原則とする。

## 8. 共通イベントエンジン

基本処理:

1. 各 `イベント_*.json` を読み込む。
2. 発生タイミングに合うイベントを抽出する。
3. 発生条件を共通条件エンジンで判定する。
4. 候補から抽選または指定イベントを提示する。
5. イベント種別に応じた共通UIを表示する。
6. 選択条件を判定して選択肢を表示する。
7. 受諾された場合、進行形式に対応する共通ハンドラーへ登録する。
8. 戦闘、移動、納品、ターン経過など既存ゲームイベントを監視して進捗を更新する。
9. 達成時に完了効果を順番に適用する。
10. 履歴・再発生・クールダウンを更新する。

---

## 9. 進行形式ハンドラー

JS側にはイベントごとの処理ではなく、形式ごとの共通処理を持つ。

概念:

```js
requestProgressHandlers = {
  即時: ...,
  納品: ...,
  討伐: ...,
  探索: ...,
  到達: ...,
  護衛: ...,
  防衛: ...,
  判定: ...,
  作業: ...,
  建設支援: ...,
  複合: ...
}
```

イベントを追加したとき、この一覧に既に存在する形式だけを使用していればコード変更は不要とする。

## 10. セーブデータ

イベント定義本文は保存しない。

保存するのはランタイム状態だけとする。

概念:

```js
eventRuntime: {
  active: [
    {
      eventId: "VILLAGE_HUMAN_ROAD_001",
      sourceId: "neutral-village-12",
      ownerPlayerId: "player-1",
      acceptedTurn: 40,
      progress: {
        current: 0,
        required: 1
      }
    }
  ],
  completed: {},
  failed: {},
  cooldownUntilTurn: {}
}
```

これによりイベント説明文や報酬表示をJSON側で修正しても、セーブデータへ定義を重複保存しない。

## 11. 一般村の友好度との接続

一般村との関係値 / 友好度は全種族共通の既存値を使う。

種族ごとに別の「堕落度」「信仰度」等の同等ゲージは作らない。

種族差はイベント定義によって表現する。

例:
- 人間: 援助、仲裁、設備復旧
- 森人: 浄化、精霊、森の保護
- 大鬼: 強敵討伐、威圧、怪力作業
- 悪魔: 契約、力の付与、生贄
- 天使: 治療、浄化、加護
- 吸血鬼: 夜間護衛、血の契約、死体引取

同じ友好度上昇でも、利用するイベントと解決方法を変えることで種族差を出す。

## 12. JSONと編集原本

ゲーム実行時は `data/source/export/json` のイベントJSONを参照する。

本プロジェクトではシート管理対象データは `@game_data` を編集原本とする運用があるため、イベントデータを正式にシート管理へ追加する場合は `SPREADSHEET_DATA_WORKFLOW.md` に従う。

現在の `scripts/game_data_converter.py` は、セル文字列が有効なJSON配列 `[...]` またはJSONオブジェクト `{...}` の場合、そのまま構造化データとして出力できる。

イベントの編集原本は、21節で採用した **1シート・1行=1イベント・番号付きセル内改行** とする。JSON配列セルをユーザーに直接編集させる案は、この入力方式で置き換える。ゲーム実行時の構造化JSONとは区別する。

イベント用シートを正式追加する際は、変換器の `SHEET_TO_JSON` と `UNIQUE_KEYS` へイベントシートを追加する。

## 15. JSON構成方針

### 15-1. 全イベントの外側構造は共通にする

イベント種別や進行形式ごとにトップレベルのJSON構造そのものを別物にはしない。

理由:
- 共通ローダーで全イベントを読める。
- スプレッドシートの列構造をイベントごとに変えなくてよい。
- UI、履歴、抽選、セーブ処理を共通化できる。
- 種類が増えてもJSON解析コードを増やさずに済む。

全イベントは原則として以下の共通構造を持つ。

```json
{
  "ID": "VILLAGE_HUMAN_ROAD_001",
  "分類": "一般村",
  "イベント種別": "依頼",
  "進行形式": "討伐",
  "名前": "街道の安全確保",
  "説明": "村と交易路の間に出没する敵を排除してほしい。",
  "発生タイミング": "一般村交流",

  "発生条件": [],
  "選択肢": [],
  "目標": [],
  "完了効果": [],
  "失敗効果": [],

  "期限ターン": null,
  "再発生": true,
  "クールダウン": 20,
  "抽選重み": 100
}
```

数値は構造説明用の仮値。

### 15-2. イベント種別は「意味」、進行形式は「処理」

`イベント種別` によってJSON構造を大きく変えない。

- `依頼`: 村等から受注するタスク
- `救援`: 危機発生から提示されるイベント
- `契約`: 条件を満たした勢力・村との契約
- `交流`: 会話・援助・特殊交流
- `支配`: 属国化・直接支配・特殊吸収などの状態遷移
- `ランダム`: ターン・探索等から自動発生するイベント

実際の進捗処理は `進行形式` で切り替える。

例えば、
- イベント種別=`依頼` / 進行形式=`討伐`
- イベント種別=`救援` / 進行形式=`防衛`
- イベント種別=`契約` / 進行形式=`即時`

のように組み合わせる。

## 16. 目標JSONの共通構造

進行形式による違いは、トップレベルではなく `目標[].設定` に閉じ込める。

単一目標でも配列として持つ。

```json
{
  "ID": "MAIN",
  "タイプ": "討伐",
  "説明": "街道を荒らす敵を討伐する",
  "必須": true,
  "順序": 1,
  "設定": {}
}
```

共通項目:

| 項目 | 内容 |
|---|---|
| `ID` | イベント内で一意な目標ID |
| `タイプ` | 討伐、納品、探索など |
| `説明` | プレイヤー向け進捗説明 |
| `必須` | 完了に必要か |
| `順序` | 複合依頼の進行順 |
| `設定` | 進行形式固有のパラメータ |

単純なイベントは `MAIN` 1件、複合イベントは複数目標を持つ。

## 17. 進行形式ごとのJSON構成

### 17-1. 即時

用途:
- 契約
- 援助を受ける / 断る
- 属国化
- 直接支配
- 高友好度の特殊交流

`即時` は継続目標を持たない。

```json
{
  "進行形式": "即時",
  "目標": []
}
```

結果は選択肢の `効果` またはイベントの `完了効果` で処理する。

例:

```json
{
  "ID": "ACCEPT",
  "名前": "契約を結ぶ",
  "選択条件": [],
  "効果": [
    {
      "タイプ": "一般村友好度変更",
      "設定": {
        "値": 10
      }
    },
    {
      "タイプ": "契約追加",
      "設定": {
        "契約ID": "DEVIL_SACRIFICE"
      }
    }
  ]
}
```

### 17-2. 納品

用途:
- 食料援助
- 資材援助
- 工具の調達
- 特定アイテムの引き渡し

```json
{
  "ID": "MAIN",
  "タイプ": "納品",
  "説明": "不足している食料を届ける",
  "必須": true,
  "順序": 1,
  "設定": {
    "納品先": "発生元",
    "必要物": [
      {
        "種別": "資源",
        "ID": "穀物",
        "数量": 50
      }
    ],
    "部分納品": true
  }
}
```

`必要物` は複数指定可能とする。

装備・アイテム納品を追加する場合も、
`種別` と `ID` を変えて同じ形式を使う。

### 17-3. 討伐

用途:
- モンスター討伐
- 盗賊排除
- 特定の強敵討伐

```json
{
  "ID": "MAIN",
  "タイプ": "討伐",
  "説明": "街道を荒らす敵を討伐する",
  "必須": true,
  "順序": 1,
  "設定": {
    "対象種別": "イベント生成敵",
    "対象ID": "ROAD_ENEMY",
    "必要数": 1,
    "判定範囲": "イベント対象"
  }
}
```

`対象種別` 候補:
- `イベント生成敵`
- `敵ID`
- `種族`
- `クラス`
- `任意敵`

特定の敵をイベント開始時に生成する場合、その生成自体は選択肢効果または開始効果として共通の `敵生成` 効果を利用する。

### 17-4. 探索

用途:
- 鉱脈調査
- 遺跡探索
- 薬草探索
- 特殊地点の調査

```json
{
  "ID": "MAIN",
  "タイプ": "探索",
  "説明": "指定地域を調査する",
  "必須": true,
  "順序": 1,
  "設定": {
    "対象種別": "イベント地点",
```

## 18. 条件JSONの共通構造

発生条件と選択条件は同じ形式を使う。

```json
{
  "タイプ": "一般村友好度",
  "比較": ">=",
  "値": 40
}
```

複数値を許可する条件では配列を使用する。

```json
{
  "タイプ": "プレイヤー種族",
  "比較": "含む",
  "値": ["悪魔", "吸血鬼"]
}
```

初期比較演算子候補:
- `一致`
- `不一致`
- `含む`
- `含まない`
- `>=`
- `<=`
- `>`
- `<`

AND / OR の正式表現は未確定のままとする。

## 20. イベント種別ごとの推奨構成

イベント種別は処理形式ではないが、データ作成時の標準形を決めておく。

| イベント種別 | 発生方法 | 選択肢 | 進行形式の代表例 |
|---|---|---|---|
| `依頼` | 村・NPCから提示 | 受諾 / 拒否を基本 | 納品、討伐、探索、到達、護衛、防衛、判定、作業、複合 |
| `救援` | 危機発生で自動提示 | 助ける / 見捨てる / 特殊行動 | 防衛、討伐、護衛、複合 |
| `契約` | 条件達成時に交流画面から提示 | 契約 / 拒否 / 条件付き選択 | 即時、判定 |
| `交流` | 村との通常交流 | 援助 / 取引 / 特殊交流 | 即時、納品、判定 |
| `支配` | 高友好度等の条件で解放 | 属国化 / 直接支配 / 種族固有支配 | 即時、判定 |
| `ランダム` | ターン・探索・地形等から発生 | イベントごとに任意 | 即時、判定、討伐、防衛、複合 |

イベント種別を増やしても、既存の進行形式で表現できる限り新しい進行ハンドラーは不要とする。

## 21. イベント編集書式（2026-10-14採用）

### 21-1. 1シート・1行=1イベント

2026-10-15: 原本へ「イベント」シートの参考テンプレートを追加済み。列は `ID / 状態 / 分類 / イベント種別 / 名前 / 説明 / 発生タイミング / 発生条件 / 選択肢 / 回答 / 条件 / 消費 / 報酬 / 効果 / 目標 / 期限ターン / 再発生 / クールダウン / 周期 / 猶予 / 備考`。各ヘッダーの注記に記載方法を置き、説明用の2行目は作らない。状態/目標/備考を含む列構成は変換器接続前の暫定テンプレートであり、4つの「参考」行はゲームに未反映。正式なキーワード・目標/契約処理の対応は接続時に確定する。

- 編集原本は `@game_data` の「イベント」1シートにまとめる。条件・選択肢・報酬のために別シートを作らず、各イベントの設定は同じ行に置く。
- 複数の選択肢・回答・条件・消費・報酬・効果を、それぞれ **1セル内の改行** でまとめてよい。1選択肢=1行へシートの行を増やす方式は採用しない。
- 入力用の番号付き文章を変換器で構造化JSONへ変換する。ゲームは生成JSONだけを参照し、原本と生成JSONを手作業で二重管理しない。
- ゲームシステム別のJSON分割は2節の方針を維持する。編集シートを1つにすることと、出力JSONを全件1ファイルにすることは別。

入力列の役割:

| 列 | 内容 |
|---|---|
| `ID` | 固定の内部イベントID。セル内の選択肢番号とは別 |
| `分類` / `イベント種別` / `名前` / `説明` | イベント全体の分類・種類・表示内容 |
| `発生タイミング` / `発生条件` | イベント全体を提示する条件 |
| `選択肢` | 番号付きの選択肢名を改行して入力 |
| `回答` | 対応する番号の回答・会話文を改行して入力 |
| `条件` | 対応する番号の選択条件。条件なしなら省略可 |
| `消費` | 対応する番号の消費物。消費なしなら省略可 |
| `報酬` | 対応する番号の報酬。報酬なしなら省略可 |
| `効果` | 対応する番号の契約開始・依頼開始等。効果なしなら省略可 |
| `期限ターン` / `再発生` / `クールダウン` / `周期` / `猶予` | 必要なイベントだけで設定する全体情報 |

目標や契約の定期処理を含む最終列構成・入力キーワード・JSON項目への対応は、変換器接続時に確定する。今回の採用だけで全イベント機能が完成した扱いにしない。

### 21-2. セル内の番号と照合

- 各項目は `番号. 内容` の形で記載する。番号は小数ではなく文字列として扱い、イベント内で照合する。
- 最初の選択肢は `1.`、`2.`、`3.`。子選択肢は `1-1.`、`1-2.`、さらに下の分岐は `1-1-1.` のように表す。
- `1-1` の親は `1`。別の「親番号」列を毎回入力せず、末尾の区切りを取り除いて親を求める。
- 入力に `1−1.` や `1－1.` を使った場合も、番号部分の区切りだけを半角 `-` へ正規化して照合する。会話本文の文字は変換しない。
- 選択肢・回答・条件・消費・報酬・効果は、同じ番号の項目を組み合わせる。セル内の行の位置が違っても、行順で誤って紐付けない。
- 空欄の条件・消費・報酬・効果は「なし」。効果等がない番号を埋めるためのダミー行は不要。同じ番号に複数の資源等を指定する場合、本文へまとめて記載し、番号自体を重複させない。

書式例（数量・条件・効果名は説明用。正式バランスや実装済みキーワード一覧ではない）:

**選択肢セル**
```text
1. 契約について聞く
1-1. 契約する
1-2. 断る
2. 依頼を受ける
```

**回答セル**
```text
1. 食料を供給してくれれば休息地を使えます。
1-1. 契約成立です。
1-2. また相談してください。
2. 木材を10個お願いします。
```

**条件セル**
```text
1-1. 友好度_30以上
```

**効果セル**
```text
1-1. 契約開始_食料供給
2. 依頼開始_木材納品
```

消費・報酬も同じ番号で記載する。複数指定の例は `穀物_50/木材_10`、`友好度_5/金_10`。記法と実際の支払タイミング・報酬確定条件は別であり、入力だけを理由に未達成依頼へ報酬を付けない。

### 21-3. 会話分岐・保存・検証

- 初期画面には親のない選択肢だけを表示する。選択した番号の回答を表示し、直接の子選択肢があればその一覧へ切り替える。
- 「戻る」は親番号から自動で用意する。表示・戻るだけでは消費や報酬・効果を再実行しない。契約/受注/報酬の二重適用防止は共通処理で維持する。
- 選択時は対応番号の条件を検査し、消費・効果を適切なタイミングで処理する。条件未達時の非表示/無効表示、分岐後の終了方法等の詳細UIは接続時に確定する。
- 内部イベントIDは初回に用意して原本へ保持し、再変換・並び替えで作り直さない。表示番号や行番号から内部イベントIDを算出しない。番号変更時の会話進捗の互換性は、契約/依頼IDの固定とは別に設計する。
- 変換時に、イベントID重複、各セル内の番号重複（正規化後を含む）、存在しない親番号、選択肢にない回答/条件/消費/報酬/効果の番号、書式不正、未知の条件/効果や存在しない資源等を検出する。誤った行を黙って別番号へ紐付けたり、未知条件を成立扱いにしたりしない。
- 現行の構造化JSONセル変換だけでは、この番号付き書式を解釈できない。イベントシート登録、番号付きセルの解析・検証、既存イベントJSONとの変換対応、会話UI接続は **未実装**。現行JSONの納品/討伐が動作することと区別する。

## 22. JSON検証方針

データ追加だけでイベントを増やすには、実行時エラーになる前にJSON定義を検証する必要がある。

最低限チェックする候補:

- ID重複
- 未知のイベント種別
- 未知の進行形式
- 未知の目標タイプ
- 未知の条件タイプ
- 未知の効果タイプ
- 進行形式と目標タイプの不一致
- 必須設定の欠落
  - 討伐なのに `必要数` がない
  - 納品なのに `必要物` がない
  - 護衛なのに `護衛対象` または `目的地` がない
- 存在しない種族・資源・技能・敵等への参照
- 複合目標のID重複
- 参照しているイベント生成物IDが存在しない

この検証はイベント内容をコードへ固定するためのものではなく、JSONの構造と参照整合性を保証するための共通検証とする。

## 23. 定期依頼と継続契約

一般村とのやり取りには、単発イベントだけでなく一定ターンごとに繰り返す関係を持たせる。

ただし、以下の2種類は分けて扱う。

### 23-1. 定期依頼

一定ターンごとに同じ種類の依頼が再提示される方式。

例:
- 10ターンごとに木材50を納品してほしい
- 15ターンごとに食料を支援してほしい
- 一定周期で周辺モンスターを掃討してほしい

これは通常の `依頼` イベントとして扱い、
完了後の `クールダウン` または `再提示周期` によって再発生させる。

概念例:

```json
{
  "イベント種別": "依頼",
  "進行形式": "納品",
  "再発生": true,
  "再提示周期": 10,
  "目標": [
    {
      "ID": "MAIN",
      "タイプ": "納品",
      "必須": true,
      "順序": 1,
      "設定": {
        "納品先": "発生元",
        "必要物": [
          {
            "種別": "資源",
            "ID": "木材",
            "数量": 50
          }
        ],
        "部分納品": true
      }
    }
  ]
}
```

`再提示周期` は「依頼完了から次に提示可能になるまでのターン数」とする候補。
既存の `クールダウン` と役割が重複するため、正式実装時にはどちらかへ統一する。

### 23-2. 継続契約

一度成立したあと、契約状態そのものをゲーム状態へ保持し、
契約中は一定ターンごとに義務と恩恵を処理する。

例:
- プレイヤーが村へ食料を定期供給する。
- 村を休息地として使用できる。
- 村から一定ターンごとに素材を受け取る。
- 悪魔が村から魂を定期的に受け取る。
- 吸血鬼が血を定期的に受け取る。
- 村が軍事支援・情報提供等を行う。

イベントは「契約を成立させる入口」であり、
成立後の継続処理は `契約Runtime` が担当する。

---

### 23-3. 資源供給と守護・力の交換（2026-10-14検討案）

魔族等には、増員に魂/死体を必要とする種族や、食料生産が苦手な種族がいる。その不足を戦闘・採取だけで埋めるのではなく、村との報酬交渉・継続契約で補えるようにする案を追加する。種族ごとの必要資源・生産適性は既存の種族/クラス/経済データを参照し、「魔族は全て同じ資源が必要」「魔族は全て食料生産が苦手」と固定しない。

| 村から得るものの候補 | プレイヤーが提供する対価の候補 |
|---|---|
| 魂の定期供納 | 村の守護、周辺脅威への対処 |
| 死体の定期供給 | 守護兵の配置、防衛への協力 |
| 穀物・野菜等の作物の定期供給 | 守護、村守備隊や住民への力の授与 |
| 生贄 | 守護や力の授与。魂/死体との関係・換算は別途確定する |

- 単発報酬ではなく、合意した期間中に一定周期で供給と義務を処理する契約として表す。どの資源を求め、守護/力のどちらを提供するかを会話の選択肢で交渉できるようにする。
- 編集は21節の1シート・1行=1イベントを維持する。例えば `1. 守護契約を提案する` の下に `1-1. 魂の供納を求める`、`1-2. 死体の供給を求める`、`1-3. 作物の供給を求める` を置き、回答・条件・契約開始効果を同じ番号で対応させる。
- 定期供給を通常の即時「報酬」と混同しない。選択直後に期間分の全資源を渡すのではなく、成立した契約へ供給元/受取先・資源・数量・期間・周期・プレイヤー側の義務を保持する。「契約内容」を番号付きの1セルにまとめる案を含め、具体的な列/入力キーワードは変換器接続時に確定する。
- 村からプレイヤーへ供給し、プレイヤーから村へ守護/力を提供する、という双方の向きを区別する。村の保有資源を渡す場合は実在庫を減らし、プレイヤーへ実際に渡せた数量だけ加算する。無から資源を増やしたり、同じ周期を重複処理したりしない。
- 魂・死体の供給元を備蓄/討伐回収/別の生成経路のどれにするか、生贄を実際の人口から出すか、その際の人数減少・幸福度・友好度・魂/死体への換算は未確定。既存の「魂の供納契約」の試作を理由に、人口消費を黙って実装しない。
- 守護の履行を派遣軍隊/滞在/討伐/村の被害等の何で判定するか、力の授与の対象・能力・持続時間、双方の不履行時の供給停止/猶予/解除、期間満了・更新・途中解除時の処理は別途決める。履行確認なしに守護済み扱いにしない。
- 数量・期間・周期・必要友好度・効果量の正式値は未確定。イベント定義へ持たせ、種族名や契約名に応じた数値をコードへ固定しない。

この節は検討案の記録であり、契約Runtime・報酬交渉・守護判定・生贄処理・強化効果が実装済みという意味ではない。既存の試作「魂の供納契約」を土台に具体化するが、今回の追記ではJSON/スプレッドシート/ゲーム処理は変更しない。

### 23-4. 交渉拒否・戦闘・再交渉（2026-10-14検討案）

23-3節の対価契約について、相手に拒否された場合の選択分岐を追加候補とする。

```text
契約を提案
  承諾 → 契約成立
  初回拒否 → 見逃す / 戦闘
    見逃す → 今回の交渉終了
    戦闘 → 実際の戦闘結果を待つ
      勝利 → 再度交渉
        承諾 → 契約成立
        再拒否 → 見逃す / 殲滅
          見逃す → 今回の交渉終了
          殲滅 → 殲滅に向けた戦闘・結果処理へ
      敗北・撤退 → 結果に応じた処理（詳細未確定）
```

- 相手の拒否だけで自動的に攻撃・殲滅しない。各段階でプレイヤーが明示的に選択する。承諾した場合は対応する契約を一度だけ成立させる。
- 初回戦闘の勝利条件は、その村の戦闘ユニットを全て倒すこととする（2026-10-14ユーザー指定）。相手と村を残して再交渉できる形で決着させ、村人口を0にする処理を勝利と同一視しない。対象戦闘ユニットの範囲・増援の扱いは接続時に確定する。
- 再交渉は戦闘開始を選んだだけでは解放せず、対象の戦闘で実際に勝利した場合のみ進める。勝利は契約の自動成立を意味しない。
- 再拒否後は見逃す/殲滅の分岐とし、戦闘と再交渉を無制限に繰り返す分岐にはしない。再提案の可否・待機期間は別途決める。
- 殲滅の対象を守備隊だけにするか住民/村まで含めるか、村・人口・魂/死体・施設・占領・周辺勢力の友好度への影響は未確定。選択直後に全住民死亡や大量資源獲得を自動適用しない。
- 番号付きセルで各選択肢・回答・条件・効果を対応させる入力方式を維持する。初回交渉/戦闘中/勝利後再交渉/再拒否/終了の段階と対象戦闘の識別を、プレイヤー・村・イベントに紐付けて保存する方針とする。画面を閉じる・ロードするだけで拒否段階を初期化し、戦闘や報酬を再実行できるようにしない。
- 撤退判定の候補は「相互の攻撃が5ターン以上なく、双方の生存戦闘ユニット間の最短距離が5マス以上」。どちらかが攻撃すれば経過をリセットし、Miss/反撃も攻撃として扱う案。撤退後も再交渉できるが友好度低下を残す案とする。撤退者の特定、再交渉までの待機期間、具体的な友好度低下量は未確定。
- 交渉方式は下記23-5節を参照。戦闘/敵対化への接続、敗北・撤退・見逃した後の関係、殲滅の完了条件は接続時に確定する。本分岐を全ての一般村会話へ無条件に適用しない。

本節も検討案の記録であり、会話・戦闘・契約・殲滅の実装完了を意味しない。

| 威圧交渉 | 威圧 | 不利益を示して要求を受け入れさせる |

### 23-6. 契約された村での他プレイヤー向け事件（2026-10-14追加方針、詳細検討中）

一方のプレイヤーが成立させた契約や威圧による村の状態を、別のプレイヤーがその村で遭遇する特殊イベントへつなげる。契約画面の当事者だけで完結する扱いにしない。

| 事件の候補 | 対象・内容 |
|---|---|
| 休息者が生贄にされる | 他プレイヤーのユニットが村で休息したことをきっかけとする事件 |
| 村からの救援要請 | 生贄・供納・強制契約等から救ってほしいと、別のプレイヤーへ依頼する |
| 契約の実態を発見 | 訪問・会話・調査等で状況を知り、救援/介入/見送るへ分岐する案 |

- 村の契約内容・交渉方式・契約の有効状態、訪問者や休息ユニットの所属、事件進行を参照する。「魔族の村だから必ず事件が起きる」と種族名だけで固定しない。威圧契約に伴う救援要請等と、生贄供給を含む契約に伴う事件を区別する。
- 上記条件に加え、村と威圧している契約先プレイヤーとの友好度で事件を分岐する。友好度が高い場合は契約先への生贄供給（休息者への強襲）、低い場合は訪れた他プレイヤーへの救援要請とする。参照するのは訪問者との友好度でもプレイヤー同士の友好度でもない。友好度だけで契約にない生贄供給を発生させない。
- 村と契約先プレイヤーとの友好度は `-100～+100` の範囲で保持し、更新結果が範囲外なら上下限に丸める。事件分岐の暫定境界は `+20以上: 生贄供給`、`-20以下: 救援要請`、`-20より大きく+20未満: 事件なし` とする。境界値は後から変更できるデータとして保持する。各分岐の発生確率は未確定で、友好度による事件の種類の判定と発生確率の抽選は分ける。同じ発生判定で強襲と救援要請を同時に起こさない。既に拘束/受け渡し待ちの対象は、友好度が変わっただけで消去や自動移転をしない。
- 友好度の高低の間には事件なしの中間帯を設ける。強襲の発生抽選は部隊の休息開始時に1回だけ行い、同じ休息中に毎ターン再抽選しない。
- クエスト達成時の友好度上昇は暫定標準値 `+10` とする。上げるのは依頼した村と達成したプレイヤーとの友好度で、別プレイヤーである契約先との友好度を一緒に上げない。部分納品/受注だけでは付与せず、完了報酬の確定時に1回だけ適用し、`+100` を超えないようにする。標準値は変更可能にし、クエスト定義で個別値を指定した場合はそちらを優先して標準値と重ねて加算しない。この方針によって既存依頼の報酬が既に変更済みという意味ではない。
- 休息は部隊単位で取り、その休息に参加する全メンバーを強襲対象にする。ランダムな1体だけを狙う方式は採用しない。村人口を強襲対象人数で割った人数を使って各対象への威力を算出する。各対象の防御・残HPでダメージ/拘束を個別判定し、耐えたメンバーは逃走・反撃を選べる。
- 契約先プレイヤー本人とその同盟プレイヤーのユニットは強襲対象から除外する。
- 救援要請の成功条件は、村を脅しているプレイヤーとの契約解除とする。契約解除後は新たな強襲と引き渡しを停止し、村が保持する生存捕虜を解放対象にする。既に引き渡した対象まで自動的に取り戻す処理とはしない。
- 契約者、被害ユニットの所有者、救援を受けたプレイヤーを別に保持する。同じ村・同じ事件の当事者を全て操作中プレイヤーに置き換えない。
- 村に関わる事件状態と、各プレイヤーが知っている情報/受注状況を区別する。事件に遭遇した側には会話・通知等で状況を伝え、未発見の契約内容や他プレイヤーの情報を無条件に全公開しない。
- 事件による魂/死体等の発生は、実際の被害・資源移転と対応させる。対象ユニットID・処理済み状態を保持し、ロード・画面再表示・プレイヤー切替で被害や報酬を二重適用しない。
- 救援を受けて契約を解除/変更した場合、元契約の定期供給・村への強化等との整合を取る必要がある。救援成功だけで新しい支配者や資源受取先を勝手に決めない。

**採用した進行（未実装）:** 村内の探索や生贄の儀式は設けず、村の強襲と契約先への受け渡しで処理する。

2026-10-14: この進行の一部を専用仮テストへ接続した。通常村への自動適用・正式シート変換・交渉判定は未接続。実際に試せる内容と仮値/制限は [`一般村イベント共通ルール.md`](./一般村イベント共通ルール.md) の「村依頼・悪魔契約の専用仮テスト」を正本とする。以下の未実装表記は正式・通常ゲームへの接続状態を指し、専用テストの対応状況と区別する。

- 強襲威力は村人口に応じて増やすが、増加は緩やかにする。1人あたりの担当人口を `村人口 / 強襲対象人数` とし、暫定式は `基準威力 × sqrt((村人口 / 強襲対象人数) / 50)`。威力を算出した後で対象人数割りする方式ではない。例: 村人口200人・対象4人なら、各対象は人口50人相当で計算する。割った人口は途中で整数に丸めず、対象人数は強襲開始時に固定して拘束結果による再配分はしない。対象0人なら強襲を実行しない。人口による威力上限は設けず、強いユニットなら大きな村でも耐えられる設計とする。基準威力は調整可能なデータとして保持する。
- 防御等を反映した最終ダメージが残HP以上なら、強襲では死亡させず拘束する。残HP未満ならダメージを受け、休息を中断して逃走・反撃等を選べる。
- 戦闘へ移る場合は村の戦闘ユニットが出てきて通常戦闘を行う。この事件で敗北した対象は、50%で死亡して死体の受け渡し対象、50%で生存拘束して受け渡し対象になる。通常戦闘全体の死亡ルールを変更するものではない。
- 契約先プレイヤーのユニットが村へ来たときに受け渡す。一定ターン経過だけで自動受け渡ししない。来訪までは村が捕虜・死体を保持し、生存者は交渉や村の戦闘ユニット撃破による救出対象とする。
- 対象の装備は捕虜の装備として残すのではなく、受け渡し時に契約先プレイヤーへ移す。死亡した対象の装備も同様。既に取られた装備は再生成せず、村で保持した実物の装備IDを移転する。捕虜・死体側と受取側に同じ装備を重複して残さない。
- 捕虜・死体・装備の保持状態と受け渡し済み状態を保存し、来訪の繰り返しやロードで再受領できないようにする。

未確定: 発生率・基準威力・その他の対象資格、危険の告知方法、戦闘敗北判定の詳細、逃走/救出・契約解除の手順、受取操作と受取後の捕虜の扱い、引き渡し前に救出した場合の装備返却と解除後の死体/装備返却、魂/死体・村人口への影響、契約者が介入する権限、友好度・敵対化・救援報酬。

## 25. 契約設定の共通項目

1つの契約に異なる周期の処理を複数持てるようにする。

例:
- 10ターンごとに食料を納品
- 毎ターン経済研究EXPを獲得
- 5ターンごとに村から素材を受領

を同じ契約内で併存可能にする。

| 項目 | 内容 |
|---|---|
| `契約ID` | 契約を一意に識別するID |
| `契約中効果` | 契約が有効な間だけ利用できる機能・状態 |
| `定期処理` | 周期の異なる支払・受取・効果を複数定義する配列 |
| `解除条件` | 自動解除する条件 |
| `解除効果` | 契約終了時に戻す機能・状態 |

`定期処理` の共通形:

```json
{
  "ID": "FOOD_PAYMENT",
  "周期": 10,
  "処理種別": "支払",
  "支払方式": "手動納品",
  "必要物": [
    {
      "種別": "資源",
      "ID": "穀物",
      "数量": 50
    }
  ],
  "履行効果": [],
  "不履行猶予": 1,
  "不履行効果": []
}
```

定期効果の例:

```json
{
  "ID": "RESEARCH_GAIN",
  "周期": 1,
  "処理種別": "効果",
  "効果": [
    {
      "タイプ": "研究EXP変更",
      "設定": {
        "技術対象": "経済",
        "値": 2
      }
    }
  ]
}
```

`技術対象` は現行 `研究.json` の `鍛冶 / 魔法 / 信仰 / 軍事 / 経済` を参照する。

### 支払方式

#### 手動納品
期限までにプレイヤーが村へ納品する。

向いている例:
- 食料援助
- 木材・石材の定期供給
- 特殊素材の供給

#### 自動徴収
周期ターンに、指定された拠点または国家資源から自動で差し引く。

向いている例:
- 定額の維持契約
- プレイヤーが毎回納品操作する必要のない小額契約

#### 支払なし
村側からの恩恵だけを受ける契約等で使用可能。
発生条件や友好度条件で制御する。

## 26. 種族ごとの契約恩恵

同じ「村との関係強化」でも、プレイヤー種族によって契約内容や恩恵を変えられる。

### 人間: 食料供給と休息地

例:
- 一定ターンごとに村へ食料を供給する。
- 契約中、その村を `休息地` として使用可能。
- 自軍ユニットが村範囲内で休息・回復できるようにする候補。
- 回復量、AP回復、補給との接続は既存回復・補給ルールを確認して別途確定する。

契約データ上は、回復数値をイベント側で重複定義せず、
`村機能解放: 休息地` のような機能解放だけを設定し、
実際の休息処理は共通ルールへ接続する。

### 悪魔: 契約と魂供給

例:
- 村との関係が一定以上で契約可能。
- 契約中、一定ターンごとに村から魂を得る。
- 魂の取得量に応じて村人口を減らすか、村で自然発生した魂を受け取るかは未確定。
- 魂1つ=資源値100という既存仕様と整合させる。

概念:

```json
{
  "契約ID": "VILLAGE_DEVIL_SOUL_TITHE",
  "契約中効果": [],
  "定期処理": [
    {
      "ID": "SOUL_TITHE",
      "周期": 10,
      "処理種別": "効果",
      "効果": [
        {
          "タイプ": "プレイヤー資源変更",
          "設定": {
            "対象": "選択拠点",
            "資源": "魂",
            "値": 100
          }
        }
      ]
    }
  ],
  "解除条件": [],
  "解除効果": []
}
```

この数値は構造説明用で未確定。

### 他種族

将来同じ契約基盤で以下のような差を作れる。

- 森人: 村周辺の森を保護する代わりに薬草・森資源・回復拠点を得る
- 土人: 鉱山技術を支援する代わりに鉱石を定期受領する
- 獣人: 狩場を守る代わりに肉・狩猟拠点を利用する
- 竜人: 軍事保護の代わりに貢物を受け取る
- 大鬼 / 巨人: 力仕事・防衛支援の代わりに大量食料や資材を受け取る
- 鬼妖: 罠・修理・裏取引の代わりに素材や情報を受け取る
- 天使: 加護・治療を提供する代わりに信仰・協力関係を得る
- 吸血鬼: 保護契約の代わりに血・死体等の特殊供給を得る

具体的な契約一覧は種族別イベントデータ作成時に確定する。

## 27. 契約Runtime

イベントRuntimeとは別に、成立済み契約の状態を保持する。

概念:

```js
contractRuntime: {
  active: [
    {
      contractId: "VILLAGE_HUMAN_FOOD_REST",
      sourceId: "neutral-village-12",
      ownerPlayerId: "player-1",
      startedTurn: 40,
      schedules: {
        FOOD_PAYMENT: {
          nextDueTurn: 50,
          unpaidCycles: 0,
          completedCycles: 0
        },
        RESEARCH_GAIN: {
          nextDueTurn: 41,
          completedCycles: 0
        }
      },
      status: "active"
    }
  ]
}
```

保持するのは契約IDと進行状態だけとし、
支払内容・周期効果・説明文等はJSON定義を参照する。

ターン処理:

1. 有効な契約の `定期処理` を確認する。
2. 各定期処理ごとの `nextDueTurn` に到達しているものを抽出する。
3. `処理種別 = 支払` なら支払方式に応じて履行を確認する。
4. `処理種別 = 効果` なら定義された効果を実行する。
5. 支払履行済みなら `履行効果` を実行する。
6. 未履行なら `不履行効果` と猶予回数を処理する。
7. 各定期処理の次回期限を個別に更新する。
8. 解除条件を満たした場合は `解除効果` を適用して契約終了する。

## 28. 契約と友好度

契約成立条件には友好度を利用できる。

契約履行:
- 友好度上昇候補
- 契約維持
- より上位の契約・属国化・特殊支配への解放条件に利用可能

契約不履行:
- 友好度低下
- 一定回数で契約解除
- 再契約クールダウン
- 種族・村の性格によっては敵対化候補

ただし具体的な数値はイベントデータ側で定義し、契約エンジンへ固定しない。

## 29. JSON検証への契約項目追加

契約イベントについて以下を追加検証する。

- `契約ID` の重複
- 各 `定期処理.ID` が契約内で重複していないか
- 各 `定期処理.周期` が1以上か
- 未知の `処理種別` / `支払方式`
- 支払・受取の資源IDが存在するか
- `契約中効果` / `定期処理.効果` / `履行効果` / `不履行効果` / `解除効果` の効果タイプが既知か
- 手動納品または自動徴収なのに支払定義がない場合の警告
- `不履行猶予` が負数でないか
- 契約追加効果が参照する `契約ID` が同イベントの `契約設定.契約ID` と一致するか


### 29-1. 種族条件の参照値

プレイヤー側と一般村側で参照元を分ける。

- `プレイヤー種族`: `種族.json.key` を使用する。
  - 例: `只人`, `エルフ`, `オーガ`, `ゴブリン`, `竜人`, `悪魔`, `天使`, `ヴァンパイア`
- `村種族`: `勢力.json.種族` を使用する。
  - 例: `人間`, `森人`, `土人`, `獣人`, `竜人`, `大鬼`, `巨人`, `鬼妖`, `悪魔`, `天使`, `吸血鬼`

人間系プレイヤーの条件へ `人間` を書くなど、参照元の異なる値を混在させない。

## 30. 村の実状態から生成する依頼

固定の「木材50」「穀物50」だけを並べるのではなく、一般村の状態から依頼内容を動的に決められるようにする。

### 30-1. 現行実装上の注意

現行の一般村実装では、プレイヤー拠点のような `foodStockByType / materialStockByType` の詳細備蓄は一般村へまだ持たせていない。

現行の一般村依頼は `v39-neutral-village-rules.js` で、
- 食料提供
- 建材提供

のどちらかを決め、必要量を村Lvから計算する簡易方式になっている。

そのため「本当に不足している資源」を使う場合は、次のどちらかを追加する必要がある。

1. 一般村にも資源在庫・需要を持たせる。
2. 一般村の7マス領域の産出と人口から、不足度を都度計算する。

初期実装は 2 を優先候補とし、将来一般村経済を詳細化した場合は実在庫を優先して不足判定する。

### 30-2. 村の産出可能資源

一般村の `territoryTileKeys` で保持している中心+周囲6マスを対象に、
各地形の `地形.json` 産出値を集計して「その村で手に入る資源」を求める。

資源名・分類はコードに重複定義せず、可能な限り `都市基本データ.json` の資源分類と `地形.json` の産出列を参照する。

用途:
- 村が得意な資源
- 村がほとんど得られない資源
- 村から返せる報酬候補
- 交易・契約候補

### 30-3. 不足資源の選択

イベントJSONに具体的な資源名を書かず、資源選択方式を書けるようにする。

概念:

```json
{
  "ID": "MAIN",
  "タイプ": "納品",
  "説明": "村で不足している資源を補給する",
  "必須": true,
  "順序": 1,
  "設定": {
    "納品先": "発生元",
    "必要物選択": {
      "方式": "村不足資源",
      "候補分類": ["食料", "一般資源", "戦略資源"],
      "不足判定": "村領域産出対人口",
      "選択数": 1
    },
    "数量設定": {
      "方式": "村規模比例"
    },
    "部分納品": true
  }
}
```

初期の `不足判定` 候補:
- `村領域産出対人口`: 7マスの産出量と人口から不足度を計算
- `実在庫`: 将来一般村が詳細在庫を持った場合に使用
- `指定分類内最低産出`: 指定分類内で最も産出が低い資源を選ぶ

具体的な不足式・数量式は未確定。

### 30-4. 村側の報酬も動的にする

依頼報酬は、村が実際に産出しやすい資源から選択可能にする。

概念:

```json
{
  "タイプ": "村産出資源受取",
  "設定": {
    "資源選択": {
      "方式": "村産出資源",
      "優先": "高産出",
      "候補分類": ["食料", "一般資源", "戦略資源", "貴重資源"],
      "選択数": 1
    },
    "数量設定": {
      "方式": "村規模比例"
    }
  }
}
```

これにより、
- 山岳村は鉱石を返しやすい
- 森の村は木材を返しやすい
- 川・湖周辺では魚を返しやすい

など、村ごとの立地差をイベント報酬へ反映できる。

## 31. プレイヤー研究を使った一般村の発展支援

一般村の依頼は「物を渡す」だけでなく、プレイヤーが持つ技術を使って村を強化できるようにする。

例:
- 防壁を建てる
- 城壁を建てる
- 見張り塔を建てる
- 道路・橋を整備する
- 将来 `柵` を施設データへ追加した場合は柵も候補にできる

現行 `施設.json` には少なくとも `防壁`、`城壁`、`見張り塔` が存在する。

### 31-1. 新しい進行形式候補: 建設支援

`作業` へ無理に詰め込まず、施設配置・研究条件・建設時間・完成後効果まで扱うため、
`進行形式 = 建設支援` を追加候補とする。

JS側ではイベント名ごとの処理ではなく、共通の `建設支援` ハンドラーが処理する。

### 31-2. JSON構成

```json
{
  "ID": "MAIN",
  "タイプ": "建設支援",
  "説明": "村の防衛設備を建設する",
  "必須": true,
  "順序": 1,
  "設定": {
    "建設先": "発生元",
    "施設候補": ["防壁", "城壁", "見張り塔"],
    "候補選択": "プレイヤーが建設可能",
    "研究条件参照": "施設.json",
    "費用参照": "施設.json",
    "建築時間参照": "施設.json",
    "配置": "一般村領域内"
  }
}
```

重要:
- 防壁等の資材費をイベントJSONへ重複記載しない。
- 必要な軍事Lv・経済Lv等も `施設.json` を参照する。
- プレイヤー側の研究進行を使って「そのプレイヤーが建設できる施設」を判定する。
- 一般村自身の研究Lvだけでなく、支援者であるプレイヤーの技術を利用できる。

### 31-3. 完成後の扱い

完成した支援施設は一般村の状態へ保持する。

概念:

```js
neutralVillage.supportFacilities = [
  {
    facilityName: "防壁",
    builtByPlayerId: "player-1",
    builtTurn: 42
  }
]
```

ただし実際の保存形式は実装時に既存拠点施設構造を確認して合わせる。
同等の既存施設状態を再利用できる場合、新しい専用配列を作らない。

施設効果もイベント側に複製せず、`施設.json` を参照する。

### 31-4. 依頼への効果

建設支援を完了した場合の候補:
- 友好度上昇
- 村守備力上昇
- 襲撃被害軽減
- 見張り塔なら索敵・襲撃発見強化
- 村が長期的に生存しやすくなる
- 上位の契約・属国化条件へ影響

どの効果を正式採用するかは未確定。

## 32. 村の依頼生成の基本方針

一般村から依頼を生成するときは、固定イベントをそのまま出すだけでなく、村の状態から候補を作れるようにする。

候補優先度の例:

1. 食料不足が大きい → 食料納品依頼
2. 建設資源不足が大きい → 資材納品依頼
3. 周囲に敵がいる → 討伐・防衛依頼
4. 防衛設備が不足し、プレイヤーが必要研究を持つ → 建設支援依頼
5. 高友好度 → 契約・長期協力イベント
6. 種族固有条件 → 種族別特殊イベント

イベントJSONは「どの状態なら候補になるか」と「候補になった後の処理」を宣言し、
実際の村状態・地形・プレイヤー研究から具体的な対象をランタイムで決める。

## 33. フィールド・村状態からの自動依頼生成

一般村の依頼は固定イベントをランダム抽選するだけではなく、
**村の不足・周辺の敵・地形・防衛状態などを評価して、その場で必要な依頼を生成する**方式を基本候補とする。

### 33-1. 依頼テンプレートと依頼インスタンスを分ける

`イベント_一般村.json` に保存するのは「依頼テンプレート」。

例:
- 不足資源を補給する
- 周辺の動物を駆除する
- 周辺のアンデッドを駆除する
- 村の防衛設備を建設する

実際に発生するときにテンプレートから「依頼インスタンス」を生成する。

例:

```js
{
  eventId: "VILLAGE_FIELD_EXTERMINATE_UNDEAD",
  instanceId: "neutral-village-12:T40:quest-1",
  sourceId: "neutral-village-12",
  generatedTurn: 40,
  resolved: {
    targetEnemyIds: ["enemy-12", "enemy-18", "enemy-21"],
    targetCount: 3,
    targetLabel: "アンデッド",
    rewardResourceId: "鉄",
    rewardAmount: 20
  }
}
```

受注後は `resolved` の内容を使う。

**受注後に周辺状況を再走査して目標を書き換えない。**

これにより、
- 対象敵が移動した
- 新しい敵が湧いた
- 村の産出量が変わった
- 別の資源不足が深刻になった

場合でも、既に提示・受注された依頼内容は変化しない。

### 33-2. 依頼生成時に見る村コンテキスト

共通の `VillageEventContext` を作り、テンプレート側はそこを参照する。

概念:

```js
{
  villageId,
  turn,
  population,
  relation,
  territoryTileKeys,
  terrainYieldByResource,
  estimatedDemandByResource,
  shortageByResource,
  nearbyEnemies,
  nearbyEnemyNests,
  supportFacilities,
  playerResearch,
  playerRace
}
```

イベントごとにマップ全体を独自走査しない。
一度作ったコンテキストを複数の依頼テンプレートで共通利用する。

## 35. 不足資源依頼の自動生成

村ごとに `shortageByResource` を計算し、不足がある場合だけ依頼候補を生成する。

処理候補:

1. 村の7マス領域から `地形.json` の資源産出を集計。
2. 人口・種族等から需要を計算。
3. `需要 - 推定産出` で不足度を算出。
4. 不足度が閾値を超える資源を候補化。
5. 最も深刻な資源、または上位N件から選択。
6. 必要数量を村規模・不足度から決定。
7. 生成時に資源IDと必要数量を `resolved` へ固定。

テンプレート例:

```json
{
  "ID": "VILLAGE_FIELD_SHORTAGE_SUPPLY",

  "イベント種別": "依頼",

  "発生タイミング": "一般村依頼生成",

  "生成設定": {
    "方式": "村不足資源",
    "候補分類": ["食料", "一般資源", "戦略資源"],
    "最低不足度": 1,
    "選択方式": "不足度最大",
    "選択数": 1,
    "数量計算": "不足度と村規模"
  },

  "目標": [
    {
      "ID": "MAIN",
      "タイプ": "納品",
      "設定": {
        "納品先": "発生元",
        "必要物参照": "resolved.requiredItems",
        "部分納品": true
      }
    }
  ]
}
```

## 36. 周辺生物・アンデッド等の駆除依頼

### 36-1. 実在する敵を対象にする

駆除依頼は、依頼のためだけに敵を新規生成する方式を基本にしない。

村周辺に既に存在する
- `state.enemies`
- `state.enemyNests`

を走査し、条件に合う実在対象から依頼を生成する。

これにより「フィールド上で実際に困っている脅威」と依頼が一致する。

### 36-2. 敵分類タグ

現行 `出現敵.json` には `巣` として、
- `死霊の巣`
- `肉食生物の巣`
- `鳥系生物の巣`
- `虫系の巣`
- `植物生物の巣`
- `飛竜の巣`



- アンデッド
- 魔獣
- 飛竜
- 虫
- 植物
- 精霊
- ゴーレム
- 人型

**種族名の文字列や敵名一覧をイベントコードへ固定定義しない。**

タグ追加を正式に行う場合は `@game_data` 側を編集原本とし、変換後の `出現敵.json` へ反映する。

現行データの `巣` は暫定的な分類補助には利用できるが、正式な依頼分類の正本にはしない。

## 38. 依頼候補の優先度

同じ村で複数の問題がある場合、すべてを同時に表示するのではなく、問題の深刻度から候補を評価する。

概念:

```text
候補スコア
= 基礎優先度
+ 不足度
+ 脅威距離補正
+ 脅威数補正
+ 緊急度
+ 種族相性補正
```

例:
- 村の隣にアンデッドがいる → 高優先度
- 7マス先に危険動物がいる → 低め
- 食料が大幅不足 → 高優先度
- 防壁がないだけ → 平時の中優先度

具体式は未確定。

JSON側にはイベントごとの `基礎優先度` と、どの評価値を加算するかだけを定義し、
共通生成エンジンが計算する形を候補とする。

## 39. 自動生成のタイミングと重複防止

依頼候補の再評価タイミング候補:
- 一般村との交流画面を開いた時
- ターン開始 / 終了時
- 村周辺で敵状態が変化した時
- 村の資源・人口状態が大きく変わった時

毎フレーム走査はしない。

同じ原因から同じ依頼を大量生成しないため、生成キーを持つ。

例:

```text
villageId + templateId + targetGroupKey
```

同じ対象敵群・同じ不足資源について、
提示中または受注中の依頼が既にある場合は新規生成しない。

対象が解決・期限切れ・依頼完了した後に、必要なら再評価する。

## 40. イベント実装前に行う一般村シミュレーション

フィールド状態から依頼を自動生成する前に、
**一般村が実際に何を不足し、どの程度の頻度で危険にさらされるかをテストプレイで確認する。**

イベント生成条件を先に固定すると、
- 実際には不足しない資源を依頼する
- 常に同じ資源だけ不足する
- 敵襲がほぼ発生しない / 多すぎる
- 守備隊が強すぎて救援依頼が発生しない
- 守備隊が弱すぎて村がすぐ消耗する

等の可能性があるため、依頼条件・報酬・優先度を決める前に一般村の基礎シミュレーションを行う。

### 40-1. 現行実装との区別

2026-09-28時点の現行実装では、一般村について以下の状態。

#### 現在動いているもの
- 一般村の人口
- 研究Lv / 研究EXP
- `勢力.json.軍隊` の人口割合から作る実守備ユニット
- 毎ターンの守備隊再同期
- プレイヤーによる一般村襲撃
- 確率抽選による外部襲撃
- 外部襲撃時の守備戦力との抽象比較
- 襲撃失敗時の人口減少
- 食料 / 建材の簡易提供依頼

#### 現在まだ接続されていないもの
- 一般村ごとの詳細な資源産出・消費・在庫
- 実際の不足資源から依頼を作る処理
- 周辺の `state.enemies` が一般村を攻撃対象として選ぶ処理
- `state.enemyNests` から一般村への実フィールド襲撃
- 実敵と一般村守備隊の直接戦闘
- 周辺敵を参照した駆除依頼の自動生成

現行の外部襲撃は、周辺に存在する敵ユニットを参照せず、
一般村ごとのターン抽選で襲撃戦力を作り、守備戦力と比較する抽象処理。

この抽象襲撃と、将来の実フィールド敵襲は別機能として評価する。

## 44. イベントシステム実装の着手条件

一般村の自動依頼生成は、少なくとも以下を確認してから本実装へ進む。

- [ ] 村領域から資源産出を算出できる
- [ ] 人口等から推定需要を算出できる
- [ ] テストUIで不足候補を確認できる
- [ ] 複数ターン進めた不足傾向を確認した
- [ ] 現行抽象襲撃の頻度・成功率・人口被害を確認した
- [ ] 村周辺の実敵・敵巣の脅威を診断できる
- [ ] どの状態を依頼生成条件として使うか決定した

この検証中は `イベント_一般村.json` を試作テンプレートとして残すが、
試作数値を正式バランス値として扱わない。

### 推奨作業順

```text
1. 一般村テスト診断を拡張
   ↓
2. 村の産出 / 推定需要 / 不足を表示
   ↓

   ↓
```

## 45. 取引・郵送・貿易の共通画面（採用方針、2026-10-14初回実装）

現行の対応範囲とテスト方法は [取引・郵送・貿易ルール.md](./取引・郵送・貿易ルール.md) を参照する。下記は採用した設計であり、遠隔承認・正式馬車/研究などの未接続部分を含む。

- 村との資源契約とプレイヤー国家間の交換を共通の取引モーダルで扱う。提示物/要求物、数量、受け渡し時期、単発/定期、周期/期間、受け渡し方法を指定する。物資量・周期が村の産出/備蓄に対して厳しいほどNPCの承諾が難しくなる。プレイヤー相手は本人の承諾/拒否/条件変更で決め、技能で強制成立させない。
- 自軍の担当ユニットを取引/郵送へ向かわせる指定機能を追加する。担当は軍隊だけでなく名前付きキャラも指定可能とする。既存のSIZによる積載・AP・地形制約を参照し、貿易だけ別の無制限輸送を作らない。既存の軍隊専用輸送機能が既に名前付きへ開放されたという意味ではない。
- 部隊に馬車等の運搬用ユニットがいる場合、その運搬用の積載量を部隊容量へ加算する。運搬用の積載量はデータで保持し、研究による解禁/容量補正は後回しとする。馬車の喪失/離脱で容量が減っても荷物は消さない。容量超過の速度倍率は `clamp(2 - 積載量 / 基礎容量 + 攻撃 / 1000, 0, 1)`。攻撃ボーナスを足した後に丸め、容量自体を増やさない。基礎容量100・攻撃500なら積載150で通常速度、200で半速、250で移動不可。部隊の基礎容量は生存メンバーの容量と馬車等の加算の合計、攻撃は生存する通常メンバーの平均を使う（運搬専用ユニットは平均から除外する方針）。基礎容量0は別処理にしてゼロ除算を防ぐ。
- 直接取引は双方が合意した取引場所へ到着し、指定時期に双方の物資を同時交換する。場所指定UIでは双方がマスと許容範囲「周囲○マス」を提示し、指定範囲の共通部分を待ち合わせ場所とする。範囲が重ならない提案は再調整が必要で、場所が合意できるまで成立させない。半径上限、共通範囲内での待機位置/荷物保管マスの選び方は調整項目とし、ユニットの重複配置を要求しない。別々の遠い指定範囲へ到着しただけで交換成立にはしない。
- 指定取引日に対して、最低3ターンの猶予を設定し、提案時に猶予ターン数を指定できる。先着側は待機し、猶予内に双方の物資/担当者が揃えば交換する。不足/未到着の判定だけで指定日直後に中止せず、猶予期限を過ぎた時点で停止・再協議へ移す。期限の判定を提案者だけのターン数にしない。期限当日の締切処理順は実装時に統一してUIへ明示する。
- 1回の取引は担当ユニット/部隊が一度に運べる量までとし、取引場所へ複数便の荷物を蓄積する方式は採用しない。取引専用の現地預かり保管も設けない。各地から出発拠点へ必要物資を集約するための輸送は可能で、担当者は出発拠点から取引場所への1便分を積む。定期貿易では交換後に出発拠点へ戻って次回分を積み、自動往復する。
- 次回1回分だけを取引専用の予約在庫として通常利用から分離する。契約成立時に必要量の1/3を手持ちの使用可能在庫から確保できなければ成立不可。整数資源の1/3は切り上げて確保する。残りは取引日までの毎ターンの実取得量から `未確保量 / 残りターン数` を目標に確保し、不足した分は翌ターンへ持ち越して再計算する。通常在庫から追加で勝手に補わず、取得前の予想収入を確保済みにしない。残りターン数0以下でもゼロ除算せず、猶予中は未確保分を実取得量の範囲で確保する。
- 複数取引は成立順に収入/在庫を確保する。先の契約の予約を除いた手持ちで次の契約の初回1/3を確保できなければ、その契約は成立不可。使用可能在庫と使用可能収入は取引用に分離した分を差し引いて表示し、詳細に総量/確保済み/未確保/次回確保目標を出す。予約在庫は維持費にも使わず、成立時に維持費を含む不足見込みを警告し、成立の判断はプレイヤーに委ねる。
- 処理順は実取得→成立順の取引分確保→残りを通常在庫へ→通常の維持費等とする。必要量以上の確保や丸めによる資源増殖を防ぐ。積み込みは予約在庫から運搬物への移転であり、二重消費しない。定期契約の次回開始でも初回1/3を確保し、できなければ中断して手動再開/再協議する（委任された細部の初期方針）。
- 郵送中の担当者は自動往復する。担当者が倒された場合、取引前なら停止する。携帯物資の死亡時処理は既存の運搬/戦利品ルールに接続し、取引停止だけで物資を元拠点へ複製しない。
- 猶予を過ぎても不足/未到着で履行できない場合は停止し、同じ取引画面で延期・条件変更・中止を再協議する。相手の再承諾まで次回分を自動請求/積み上げない。
- 中止時、未受け渡しの担当者は物資を携帯して引き返す。未積載の予約は解除するが、運搬中の物資は実際の帰還/荷下ろしで通常在庫へ戻す。既に渡した物資は一方的に巻き戻さず、返却等の交渉を必要とする。取引/配送の単位ごとに未受け渡し/受け渡し済みを記録する。中断後の再開は条件/担当者を確認して手動で行う。
- 生贄/捕虜/死体の受領は既に採用した来訪引き渡しを維持し、資源同時交換で自動消費しない。村の魂供給元は人口から無断生成せず、初期実装では実在庫を使う。NPCの承諾式と馬車の能力値等は明示した仮設定で開始する。

現行積載の確認: `v39-logistics-state.js` はユニットの `status.SIZ`（なければ `SIZ`）から `100 × SIZ / 170 + cargoCapacityBonus` を小数1桁に丸めて容量を計算する。資源は種類別の数量を合計し、装備は運搬配列の1行を1として加える。軍隊の編成人数はこの容量関数では直接掛けない。既存の集積所輸送指定は非名前付き軍隊に限定されるが、新しい取引担当は名前付きにも対応し、容量加算と超過時のAPコスト補正を接続済み。
