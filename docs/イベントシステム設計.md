# イベントシステム設計

> 状態: 設計中 / 未実装
>
> 目的: 一般村依頼を最初の利用対象として、イベント内容をデータ追加だけで増やせる共通イベント基盤を設計する。
>
> 現時点では実装仕様を確定するための設計資料であり、現行挙動を示す資料ではない。

---

## 1. 基本方針

- イベントごとの固有処理をJSへ追加する方式にはしない。
- ランタイムはイベント定義JSONを読み、共通の条件判定・進行管理・結果適用を行う。
- 新規イベントが既存の条件タイプ・進行形式・効果タイプだけで表現できる場合、JS修正なしで追加できることを目標とする。
- 新しい仕組みが必要な場合だけ、共通の「進行形式」または「効果タイプ」を1つ追加する。
- 種族名、イベント名、報酬量、必要数などをコードへ固定定義しない。
- セーブデータにはイベント定義そのものを複製せず、イベントIDと進行状況だけを保持する。
- 最初の対象は一般村イベントとするが、将来は探索、都市、外交、国家、災害等でも同じエンジンを利用できる構造にする。

---

## 2. ファイル分割方針

イベントは全件を1ファイルへ集約せず、**ゲームシステム単位**で分ける。

初期候補:

- `イベント_一般村.json`
- `イベント_探索.json`
- `イベント_都市.json`
- `イベント_外交.json`
- `イベント_国家.json`

種族ごとのファイル分割は行わない。

理由:
- 共通イベントや複数種族対象イベントの置き場所が曖昧にならない。
- 「一般村イベントを全部確認する」ときに複数ファイルを横断しなくてよい。
- 種族差は発生条件として定義できる。

報酬も原則イベント定義内に持つ。

同じランダム報酬セットを多数のイベントが共有する必要が生じた場合のみ、将来 `報酬テーブル.json` の追加を検討する。

## 3. 「イベント種別」と「進行形式」を分離する

### 3-1. イベント種別

イベントがゲーム上で何を意味するかを表す。

初期候補:

- `依頼`
- `救援`
- `契約`
- `交流`
- `支配`
- `ランダム`

これは主に、
- UI表示
- イベント一覧の分類
- 発生タイミング
- AIや村側の提示方法

に使う。

### 3-2. 進行形式

イベントを**どう進め、何をもって完了とするか**を決める。

初期候補:

| 進行形式 | 用途 | 例 |
|---|---|---|
| `即時` | 選択した時点で結果を適用 | 契約を結ぶ、援助を断る |
| `納品` | 指定資源・装備等を渡す | 食料50を届ける |
| `討伐` | 指定対象を指定数倒す | マンティコア1体討伐 |
| `探索` | 指定地点・地形・対象を調査する | 鉱脈調査、遺跡探索 |
| `到達` | 指定地点へユニットが到達する | 村人の捜索地点へ向かう |
| `護衛` | 対象を目的地まで生存させる | 貢物護送、避難民護衛 |
| `防衛` | 指定対象を一定条件まで守る | 村への襲撃を撃退 |
| `判定` | 指定技能等で判定する | 仲裁、威圧、浄化 |
| `作業` | 指定地点でAP・ターン・資源等を使って作業する | 橋修理、巨岩撤去 |
| `複合` | 複数目標を組み合わせる | 救出地点へ到達→敵討伐→村へ帰還 |

重要:
- 種族やイベント固有名で処理を分けない。
- `進行形式` に対応する共通ハンドラーで処理する。
- `複合` は専用イベント処理を書かず、既存の目標タイプを複数並べて処理する。

## 4. 一般村イベントでの例

### 人間: 街道の安全確保

- イベント種別: `依頼`
- 進行形式: `討伐`
- プレイヤー種族条件: 人間
- 目標: 指定された敵を倒す
- 完了結果: 一般村友好度上昇 + 報酬

### 人間: 不足物資の援助

- イベント種別: `依頼`
- 進行形式: `納品`
- プレイヤー種族条件: 人間
- 目標: 指定資源を村へ渡す
- 完了結果: 一般村友好度上昇

### 悪魔: 生贄の契約

- イベント種別: `契約`
- 進行形式: `即時`
- プレイヤー種族条件: 悪魔
- 友好度等の発生条件を満たした場合のみ提示
- 選択結果として人口、魂、友好度、契約状態等を変更可能にする

### 竜人: 貢物の護送

- イベント種別: `依頼`
- 進行形式: `護衛`
- 村から護送対象を生成または参照
- 指定地点まで生存させると完了

### 人間: 村人の救出

単純な1形式で表現できない場合は `複合` とする。

例:
1. 救出地点へ `到達`
2. 周辺の敵を `討伐`
3. 生存者を村まで `護衛`

## 6. 条件を3種類に分ける

条件は用途を混在させない。

### 6-1. 発生条件

イベント自体を候補に入れる条件。

例:
- プレイヤー種族
- 村種族
- 一般村友好度
- 一般村人口
- 属国状態
- 地形
- 研究Lv
- 資源量
- 周辺の敵存在
- 過去イベント完了
- ターン数

### 6-2. 選択条件

イベントは表示されているが、その選択肢を使用できるかを決める条件。

例:
- 穀物50以上を所持
- 交渉50以上
- 特定スキルを所持
- 友好度80以上

満たしていない選択肢を非表示にするか、無効表示にするかはUI設計時に確定する。

### 6-3. 達成条件 / 目標

受諾後に何を完了すればよいかを表す。

例:
- 対象敵を3体討伐
- 指定資源を50納品
- 指定マスへ到達
- 3ターン防衛
- NPCを目的地へ護衛

## 7. 効果タイプ

イベントの結果は共通の効果ハンドラーで処理する。

初期候補:

- `一般村友好度変更`
- `一般村人口変更`
- `プレイヤー資源変更`
- `一般村資源変更`
- `研究EXP変更`
- `敵生成`
- `放浪者生成`
- `ユニット生成`
- `状態追加`
- `契約追加`
- `属国化`
- `直接支配`
- `イベント開始`

イベント固有のJS関数名をJSONへ直接書かず、登録済みの効果タイプから選ぶことを原則とする。

## 8. 共通イベントエンジン

基本処理:

1. 各 `イベント_*.json` を読み込む。
2. 発生タイミングに合うイベントを抽出する。
3. 発生条件を共通条件エンジンで判定する。
4. 候補から抽選または指定イベントを提示する。
5. イベント種別に応じた共通UIを表示する。
6. 選択条件を判定して選択肢を表示する。
7. 受諾された場合、進行形式に対応する共通ハンドラーへ登録する。
8. 戦闘、移動、納品、ターン経過など既存ゲームイベントを監視して進捗を更新する。
9. 達成時に完了効果を順番に適用する。
10. 履歴・再発生・クールダウンを更新する。

---

## 9. 進行形式ハンドラー

JS側にはイベントごとの処理ではなく、形式ごとの共通処理を持つ。

概念:

```js
requestProgressHandlers = {
  即時: ...,
  納品: ...,
  討伐: ...,
  探索: ...,
  到達: ...,
  護衛: ...,
  防衛: ...,
  判定: ...,
  作業: ...,
  複合: ...
}
```

イベントを追加したとき、この一覧に既に存在する形式だけを使用していればコード変更は不要とする。

## 10. セーブデータ

イベント定義本文は保存しない。

保存するのはランタイム状態だけとする。

概念:

```js
eventRuntime: {
  active: [
    {
      eventId: "VILLAGE_HUMAN_ROAD_001",
      sourceId: "neutral-village-12",
      ownerPlayerId: "player-1",
      acceptedTurn: 40,
      progress: {
        current: 0,
        required: 1
      }
    }
  ],
  completed: {},
  failed: {},
  cooldownUntilTurn: {}
}
```

これによりイベント説明文や報酬表示をJSON側で修正しても、セーブデータへ定義を重複保存しない。

## 11. 一般村の友好度との接続

一般村との関係値 / 友好度は全種族共通の既存値を使う。

種族ごとに別の「堕落度」「信仰度」等の同等ゲージは作らない。

種族差はイベント定義によって表現する。

例:
- 人間: 援助、仲裁、設備復旧
- 森人: 浄化、精霊、森の保護
- 大鬼: 強敵討伐、威圧、怪力作業
- 悪魔: 契約、力の付与、生贄
- 天使: 治療、浄化、加護
- 吸血鬼: 夜間護衛、血の契約、死体引取

同じ友好度上昇でも、利用するイベントと解決方法を変えることで種族差を出す。

## 12. JSONと編集原本

ゲーム実行時は `data/source/export/json` のイベントJSONを参照する。

本プロジェクトではシート管理対象データは `@game_data` を編集原本とする運用があるため、イベントデータを正式にシート管理へ追加する場合は `SPREADSHEET_DATA_WORKFLOW.md` に従う。

現在の `scripts/game_data_converter.py` は、セル文字列が有効なJSON配列 `[...]` またはJSONオブジェクト `{...}` の場合、そのまま構造化データとして出力できる。

そのためイベントはスプレッドシート上で1イベント=1行とし、`発生条件`、`選択肢`、`目標`、`完了効果`、`失敗効果` などのネスト項目をJSON配列セルとして保持する方針を第一候補とする。

イベント用シートを正式追加する際は、変換器の `SHEET_TO_JSON` と `UNIQUE_KEYS` へイベントシートを追加する。

## 15. JSON構成方針

### 15-1. 全イベントの外側構造は共通にする

イベント種別や進行形式ごとにトップレベルのJSON構造そのものを別物にはしない。

理由:
- 共通ローダーで全イベントを読める。
- スプレッドシートの列構造をイベントごとに変えなくてよい。
- UI、履歴、抽選、セーブ処理を共通化できる。
- 種類が増えてもJSON解析コードを増やさずに済む。

全イベントは原則として以下の共通構造を持つ。

```json
{
  "ID": "VILLAGE_HUMAN_ROAD_001",
  "分類": "一般村",
  "イベント種別": "依頼",
  "進行形式": "討伐",
  "名前": "街道の安全確保",
  "説明": "村と交易路の間に出没する敵を排除してほしい。",
  "発生タイミング": "一般村交流",

  "発生条件": [],
  "選択肢": [],
  "目標": [],
  "完了効果": [],
  "失敗効果": [],

  "期限ターン": null,
  "再発生": true,
  "クールダウン": 20,
  "抽選重み": 100
}
```

数値は構造説明用の仮値。

### 15-2. イベント種別は「意味」、進行形式は「処理」

`イベント種別` によってJSON構造を大きく変えない。

- `依頼`: 村等から受注するタスク
- `救援`: 危機発生から提示されるイベント
- `契約`: 条件を満たした勢力・村との契約
- `交流`: 会話・援助・特殊交流
- `支配`: 属国化・直接支配・特殊吸収などの状態遷移
- `ランダム`: ターン・探索等から自動発生するイベント

実際の進捗処理は `進行形式` で切り替える。

例えば、
- イベント種別=`依頼` / 進行形式=`討伐`
- イベント種別=`救援` / 進行形式=`防衛`
- イベント種別=`契約` / 進行形式=`即時`

のように組み合わせる。

## 16. 目標JSONの共通構造

進行形式による違いは、トップレベルではなく `目標[].設定` に閉じ込める。

単一目標でも配列として持つ。

```json
{
  "ID": "MAIN",
  "タイプ": "討伐",
  "説明": "街道を荒らす敵を討伐する",
  "必須": true,
  "順序": 1,
  "設定": {}
}
```

共通項目:

| 項目 | 内容 |
|---|---|
| `ID` | イベント内で一意な目標ID |
| `タイプ` | 討伐、納品、探索など |
| `説明` | プレイヤー向け進捗説明 |
| `必須` | 完了に必要か |
| `順序` | 複合依頼の進行順 |
| `設定` | 進行形式固有のパラメータ |

単純なイベントは `MAIN` 1件、複合イベントは複数目標を持つ。

## 17. 進行形式ごとのJSON構成

### 17-1. 即時

用途:
- 契約
- 援助を受ける / 断る
- 属国化
- 直接支配
- 高友好度の特殊交流

`即時` は継続目標を持たない。

```json
{
  "進行形式": "即時",
  "目標": []
}
```

結果は選択肢の `効果` またはイベントの `完了効果` で処理する。

例:

```json
{
  "ID": "ACCEPT",
  "名前": "契約を結ぶ",
  "選択条件": [],
  "効果": [
    {
      "タイプ": "一般村友好度変更",
      "設定": {
        "値": 10
      }
    },
    {
      "タイプ": "契約追加",
      "設定": {
        "契約ID": "DEVIL_SACRIFICE"
      }
    }
  ]
}
```

### 17-2. 納品

用途:
- 食料援助
- 資材援助
- 工具の調達
- 特定アイテムの引き渡し

```json
{
  "ID": "MAIN",
  "タイプ": "納品",
  "説明": "不足している食料を届ける",
  "必須": true,
  "順序": 1,
  "設定": {
    "納品先": "発生元",
    "必要物": [
      {
        "種別": "資源",
        "ID": "穀物",
        "数量": 50
      }
    ],
    "部分納品": true
  }
}
```

`必要物` は複数指定可能とする。

装備・アイテム納品を追加する場合も、
`種別` と `ID` を変えて同じ形式を使う。

### 17-3. 討伐

用途:
- モンスター討伐
- 盗賊排除
- 特定の強敵討伐

```json
{
  "ID": "MAIN",
  "タイプ": "討伐",
  "説明": "街道を荒らす敵を討伐する",
  "必須": true,
  "順序": 1,
  "設定": {
    "対象種別": "イベント生成敵",
    "対象ID": "ROAD_ENEMY",
    "必要数": 1,
    "判定範囲": "イベント対象"
  }
}
```

`対象種別` 候補:
- `イベント生成敵`
- `敵ID`
- `種族`
- `クラス`
- `任意敵`

特定の敵をイベント開始時に生成する場合、その生成自体は選択肢効果または開始効果として共通の `敵生成` 効果を利用する。

### 17-4. 探索

用途:
- 鉱脈調査
- 遺跡探索
- 薬草探索
- 特殊地点の調査

```json
{
  "ID": "MAIN",
  "タイプ": "探索",
  "説明": "指定地域を調査する",
  "必須": true,
  "順序": 1,
  "設定": {
    "対象種別": "イベント地点",
    "対象ID": "SEARCH_POINT_01",
    "必要回数": 1,
    "使用処理": "既存調査"
  }
}
```

探索そのもののAP消費・調査処理は、既存のフィールド調査ルールを再利用する。
イベント側へ同じAP値を重複定義しない。

### 17-5. 到達

用途:
- 指定地点への移動
- 捜索地点への到着
- 村への帰還

```json
{
  "ID": "MAIN",
  "タイプ": "到達",
  "説明": "指定地点へ向かう",
  "必須": true,
  "順序": 1,
  "設定": {
    "目的地種別": "イベント地点",
    "目的地ID": "TARGET_POINT_01",
    "到達対象": "任意自軍ユニット",
    "必要数": 1
  }
}
```

`目的地種別` 候補:
- `イベント地点`
- `発生元`
- `一般村`
- `拠点`
- `指定座標`

座標を直接固定する必要がある場合だけ座標を使用し、通常はランタイム生成した地点IDを参照する。

### 17-6. 護衛

用途:
- 村人救出
- 貢物護送
- 避難民護衛

```json
{
  "ID": "MAIN",

  "説明": "護衛対象を目的地まで送り届ける",
  "必須": true,
  "順序": 1,
  "設定": {
    "護衛対象種別": "イベントNPC",
    "護衛対象ID": "ESCORT_TARGET_01",
    "目的地種別": "発生元",
    "目的地ID": null,
    "必要生存数": 1
  }
}
```

護衛対象の移動方式は未確定。
JSONには目的と条件だけを持ち、AI移動ロジックそのものは共通護衛処理へ置く。

### 17-7. 防衛

用途:
- 一般村防衛
- 拠点防衛
- 一定ターンの護持

```json
{
  "ID": "MAIN",
  "タイプ": "防衛",
  "説明": "村を襲撃から守る",
  "必須": true,
  "順序": 1,
  "設定": {
    "防衛対象種別": "発生元",

    "必要ターン": 3,

      {

      }

  }
}
```

敵の生成数・種類は防衛目標へ直接埋め込まず、イベント開始時の `敵生成` 効果として定義可能にする。

### 17-8. 判定

用途:
- 仲裁
- 威圧
- 交渉
- 技術作業の成否
- 浄化判定

```json
{
  "ID": "MAIN",
  "タイプ": "判定",
  "説明": "交渉で争いを収める",
  "必須": true,
  "順序": 1,
  "設定": {
    "判定者": "選択ユニット",
    "技能": "交渉",
    "難易度": 50,
    "必要成功数": 1,
```

- 聖域再建

```json
      "タイプ": "討伐",
      "説明": "周囲の敵を排除する",
      "必須": true,
      "順序": 2,
      "設定": {
        "対象種別": "イベント生成敵",
```

## 18. 条件JSONの共通構造

発生条件と選択条件は同じ形式を使う。

```json
{
  "タイプ": "一般村友好度",
  "比較": ">=",
  "値": 40
}
```

複数値を許可する条件では配列を使用する。

```json
{
  "タイプ": "プレイヤー種族",
  "比較": "含む",
  "値": ["悪魔", "吸血鬼"]
}
```

初期比較演算子候補:
- `一致`
- `不一致`
- `含む`
- `含まない`
- `>=`
- `<=`
- `>`
- `<`

AND / OR の正式表現は未確定のままとする。

## 19. 効果JSONの共通構造

効果も、共通部とタイプ別 `設定` に分ける。

```json
{
  "タイプ": "一般村友好度変更",
  "設定": {
    "値": 10
  }
}
```

資源変更:

```json
{
  "タイプ": "プレイヤー資源変更",
  "設定": {
    "対象": "選択拠点",
    "資源": "魂",
    "値": 100
  }
}
```

敵生成:

```json
{
  "タイプ": "敵生成",
  "設定": {
    "参照ID": "ROAD_ENEMY",
    "生成元": "出現敵",
    "生成条件": {
      "種族名": "マンティコア"
    },
    "数": 1,
    "配置": "発生元周辺"

```

`参照ID` を付けた生成物は、同一イベント内の目標から参照できるようにする。

イベント固有の関数名はJSONへ書かない。

## 20. イベント種別ごとの推奨構成

イベント種別は処理形式ではないが、データ作成時の標準形を決めておく。

| イベント種別 | 発生方法 | 選択肢 | 進行形式の代表例 |
|---|---|---|---|
| `依頼` | 村・NPCから提示 | 受諾 / 拒否を基本 | 納品、討伐、探索、到達、護衛、防衛、判定、作業、複合 |
| `救援` | 危機発生で自動提示 | 助ける / 見捨てる / 特殊行動 | 防衛、討伐、護衛、複合 |
| `契約` | 条件達成時に交流画面から提示 | 契約 / 拒否 / 条件付き選択 | 即時、判定 |
| `交流` | 村との通常交流 | 援助 / 取引 / 特殊交流 | 即時、納品、判定 |
| `支配` | 高友好度等の条件で解放 | 属国化 / 直接支配 / 種族固有支配 | 即時、判定 |
| `ランダム` | ターン・探索・地形等から発生 | イベントごとに任意 | 即時、判定、討伐、防衛、複合 |

イベント種別を増やしても、既存の進行形式で表現できる限り新しい進行ハンドラーは不要とする。

## 21. @game_data シート上の構成案

現在の `scripts/game_data_converter.py` は、セル文字列が有効なJSON配列 `[...]` またはJSONオブジェクト `{...}` の場合、そのまま構造化データとしてJSONへ出力できる。

そのためイベント用シートは、**1イベント = 1行**を維持する。

初期列案:

| 列 | 内容 |
|---|---|
| `ID` | 一意なイベントID |
| `分類` | 一般村、探索など |
| `イベント種別` | 依頼、救援、契約など |
| `進行形式` | 即時、納品、討伐など |
| `名前` | 表示名 |
| `説明` | 本文 |
| `発生タイミング` | 交流時、ターン時等 |
| `発生条件` | JSON配列セル |
| `選択肢` | JSON配列セル |
| `目標` | JSON配列セル |
| `目標進行` | 単一 / 順番 / 並行。必要時のみ |
| `完了効果` | JSON配列セル |
| `失敗効果` | JSON配列セル |
| `期限ターン` | 任意 |
| `再発生` | Boolean |
| `クールダウン` | 任意 |
| `抽選重み` | 任意 |

例として、スプレッドシートの `目標` セルへ以下の文字列を入れる。

```json
[{"ID":"MAIN","タイプ":"討伐","説明":"敵を討伐する","必須":true,"順序":1,"設定":{"対象種別":"イベント生成敵","対象ID":"ROAD_ENEMY","必要数":1,"判定範囲":"イベント対象"}}]
```

変換器はこのセルを文字列のまま出さず、JSON配列として出力する。

実装時に必要な変換器変更:
- イベント用シートを `SHEET_TO_JSON` へ追加する。
- `UNIQUE_KEYS` に `ID` を追加する。
- 必要ならイベント用の追加検証を実装する。

イベントのネスト構造そのものを出力するための新しい変換器は不要で、現行の構造化セル変換を利用できる。

## 22. JSON検証方針

データ追加だけでイベントを増やすには、実行時エラーになる前にJSON定義を検証する必要がある。

最低限チェックする候補:

- ID重複
- 未知のイベント種別
- 未知の進行形式
- 未知の目標タイプ
- 未知の条件タイプ
- 未知の効果タイプ
- 進行形式と目標タイプの不一致
- 必須設定の欠落
  - 討伐なのに `必要数` がない
  - 納品なのに `必要物` がない
  - 護衛なのに `護衛対象` または `目的地` がない
- 存在しない種族・資源・技能・敵等への参照
- 複合目標のID重複
- 参照しているイベント生成物IDが存在しない

この検証はイベント内容をコードへ固定するためのものではなく、JSONの構造と参照整合性を保証するための共通検証とする。

## 23. 定期依頼と継続契約

一般村とのやり取りには、単発イベントだけでなく一定ターンごとに繰り返す関係を持たせる。

ただし、以下の2種類は分けて扱う。

### 23-1. 定期依頼

一定ターンごとに同じ種類の依頼が再提示される方式。

例:
- 10ターンごとに木材50を納品してほしい
- 15ターンごとに食料を支援してほしい
- 一定周期で周辺モンスターを掃討してほしい

これは通常の `依頼` イベントとして扱い、
完了後の `クールダウン` または `再提示周期` によって再発生させる。

概念例:

```json
{
  "イベント種別": "依頼",
  "進行形式": "納品",
  "再発生": true,
  "再提示周期": 10,
  "目標": [
    {
      "ID": "MAIN",
      "タイプ": "納品",
      "必須": true,
      "順序": 1,
      "設定": {
        "納品先": "発生元",
        "必要物": [
          {
            "種別": "資源",
            "ID": "木材",
            "数量": 50
          }
        ],
        "部分納品": true
      }
    }
  ]
}
```

`再提示周期` は「依頼完了から次に提示可能になるまでのターン数」とする候補。
既存の `クールダウン` と役割が重複するため、正式実装時にはどちらかへ統一する。

### 23-2. 継続契約

一度成立したあと、契約状態そのものをゲーム状態へ保持し、
契約中は一定ターンごとに義務と恩恵を処理する。

例:
- プレイヤーが村へ食料を定期供給する。
- 村を休息地として使用できる。
- 村から一定ターンごとに素材を受け取る。
- 悪魔が村から魂を定期的に受け取る。
- 吸血鬼が血を定期的に受け取る。
- 村が軍事支援・情報提供等を行う。

イベントは「契約を成立させる入口」であり、
成立後の継続処理は `契約Runtime` が担当する。

## 24. 契約JSON構成

契約イベントは `イベント種別 = 契約` とし、
契約成立時の選択肢効果から `契約追加` を実行する。

契約の内容はイベント内の `契約設定` に持たせる。

概念:

```json
{
  "ID": "VILLAGE_HUMAN_FOOD_REST_001",
  "分類": "一般村",
  "イベント種別": "契約",
  "進行形式": "即時",
  "名前": "食料供給契約",
  "説明": "定期的に食料を供給する代わりに、この村を休息地として利用する。",

  "発生条件": [
    {
      "タイプ": "プレイヤー種族",
      "比較": "一致",
      "値": "人間"
    }
  ],

  "選択肢": [
    {
      "ID": "ACCEPT",
      "名前": "契約する",
      "選択条件": [],
      "効果": [
        {
          "タイプ": "契約追加",
          "設定": {
            "契約ID": "VILLAGE_HUMAN_FOOD_REST"
          }
        }
      ]
    }
  ],

  "契約設定": {
    "契約ID": "VILLAGE_HUMAN_FOOD_REST",
    "周期": 10,
    "支払方式": "手動納品",
    "支払": [
      {
        "種別": "資源",
        "ID": "穀物",
        "数量": 50
      }
    ],
    "成立効果": [
      {
        "タイプ": "村機能解放",
        "設定": {
          "機能": "休息地"
        }
      }
    ],
    "周期効果": [],
    "不履行猶予": 1,
    "不履行効果": [
      {
        "タイプ": "一般村友好度変更",
        "設定": {
          "値": -5
        }
      }
    ],
    "解除効果": []
  }
}
```

数値は説明用の仮値。

## 25. 契約設定の共通項目

| 項目 | 内容 |
|---|---|
| `契約ID` | 契約を一意に識別するID |
| `周期` | 何ターンごとに契約処理するか |
| `支払方式` | 手動納品 / 自動徴収 / 支払なし |
| `支払` | プレイヤー側から村へ渡す資源等 |
| `受取` | 村側からプレイヤーへ渡す資源等 |
| `成立効果` | 契約中ずっと有効にする機能解放・状態 |
| `周期効果` | 周期到達時に毎回実行する効果 |
| `不履行猶予` | 支払不能から何周期まで契約を維持するか |
| `不履行効果` | 未納時の友好度低下など |
| `解除条件` | 自動解除する条件 |
| `解除効果` | 契約終了時に戻す機能・状態 |

### 支払方式

#### 手動納品
期限までにプレイヤーが村へ納品する。

向いている例:
- 食料援助
- 木材・石材の定期供給
- 特殊素材の供給

#### 自動徴収
周期ターンに、指定された拠点または国家資源から自動で差し引く。

向いている例:
- 定額の維持契約
- プレイヤーが毎回納品操作する必要のない小額契約

#### 支払なし
村側からの恩恵だけを受ける契約等で使用可能。
発生条件や友好度条件で制御する。

## 26. 種族ごとの契約恩恵

同じ「村との関係強化」でも、プレイヤー種族によって契約内容や恩恵を変えられる。

### 人間: 食料供給と休息地

例:
- 一定ターンごとに村へ食料を供給する。
- 契約中、その村を `休息地` として使用可能。
- 自軍ユニットが村範囲内で休息・回復できるようにする候補。
- 回復量、AP回復、補給との接続は既存回復・補給ルールを確認して別途確定する。

契約データ上は、回復数値をイベント側で重複定義せず、
`村機能解放: 休息地` のような機能解放だけを設定し、
実際の休息処理は共通ルールへ接続する。

### 悪魔: 契約と魂供給

例:
- 村との関係が一定以上で契約可能。
- 契約中、一定ターンごとに村から魂を得る。
- 魂の取得量に応じて村人口を減らすか、村で自然発生した魂を受け取るかは未確定。
- 魂1つ=資源値100という既存仕様と整合させる。

概念:

```json
{
  "契約ID": "VILLAGE_DEVIL_SOUL_TITHE",
  "周期": 10,
  "支払方式": "支払なし",
  "受取": [],
  "周期効果": [
    {
      "タイプ": "プレイヤー資源変更",
      "設定": {
        "対象": "選択拠点",
        "資源": "魂",
        "値": 100
      }
    }
  ]
}
```

この数値は構造説明用で未確定。

### 他種族

将来同じ契約基盤で以下のような差を作れる。

- 森人: 村周辺の森を保護する代わりに薬草・森資源・回復拠点を得る
- 土人: 鉱山技術を支援する代わりに鉱石を定期受領する
- 獣人: 狩場を守る代わりに肉・狩猟拠点を利用する
- 竜人: 軍事保護の代わりに貢物を受け取る
- 大鬼 / 巨人: 力仕事・防衛支援の代わりに大量食料や資材を受け取る
- 鬼妖: 罠・修理・裏取引の代わりに素材や情報を受け取る
- 天使: 加護・治療を提供する代わりに信仰・協力関係を得る
- 吸血鬼: 保護契約の代わりに血・死体等の特殊供給を得る

具体的な契約一覧は種族別イベントデータ作成時に確定する。

## 27. 契約Runtime

イベントRuntimeとは別に、成立済み契約の状態を保持する。

概念:

```js
contractRuntime: {
  active: [
    {
      contractId: "VILLAGE_HUMAN_FOOD_REST",
      sourceId: "neutral-village-12",
      ownerPlayerId: "player-1",
      startedTurn: 40,
      nextDueTurn: 50,
      unpaidCycles: 0,
      completedCycles: 0,
      status: "active"
    }
  ]
}
```

保持するのは契約IDと進行状態だけとし、
支払内容・周期効果・説明文等はJSON定義を参照する。

ターン処理:

1. `nextDueTurn` に到達した契約を抽出。
2. 支払方式を確認。
3. 自動徴収なら資源を確認して支払い。
4. 手動納品なら納品済み状態を確認。
5. 履行済みなら `周期効果` を実行。
6. 未履行なら `不履行効果` と猶予回数を処理。
7. 解除条件を満たした場合は `解除効果` を適用して契約終了。
8. 継続する場合は次回期限を更新。

---

## 28. 契約と友好度

契約成立条件には友好度を利用できる。

契約履行:
- 友好度上昇候補
- 契約維持
- より上位の契約・属国化・特殊支配への解放条件に利用可能

契約不履行:
- 友好度低下
- 一定回数で契約解除
- 再契約クールダウン
- 種族・村の性格によっては敵対化候補

ただし具体的な数値はイベントデータ側で定義し、契約エンジンへ固定しない。

## 29. JSON検証への契約項目追加

契約イベントについて以下を追加検証する。

- `契約ID` の重複
- `周期` が1以上か
- 未知の `支払方式`
- 支払・受取の資源IDが存在するか
- `成立効果` / `周期効果` / `不履行効果` / `解除効果` の効果タイプが既知か
- 手動納品または自動徴収なのに支払定義がない場合の警告
- `不履行猶予` が負数でないか
- 契約追加効果が参照する `契約ID` が同イベントの `契約設定.契約ID` と一致するか
