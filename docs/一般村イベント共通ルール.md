# 一般村イベント共通ルール

更新: 2026-10-21 / UI53。現在の一般村依頼と計画の実行ルールです。旧方式の説明は履歴へ分離しました。

## 原本と依頼生成

- UI58: 初期目標は「村→墓地→食料生産」。施設シートの前提/優先度と候補地の実増産量を村の自動建設へ接続。費用/期間/地形/研究は既存の施設データ、物資/討伐支援は既存イベントのひな型を使う。config/v39-village-development.jsonの4項目は状態表示用の節目で、別建設キューを動かさない。
- 完了時点は `planSchedule.development.completedById` に保存する。安全・食料・守備の条件が再び不足したら対応する段階を再開し、後続は前提待ちにする。墓地は死体がなくても前提達成後に通常の費用・工期で建設する。支援は不足分を埋め、建設/訓練の通常処理を経て完了する。
- 村モーダル「情報」に発展経路の前提・状態・不足量を表示する。専用「村の計画・支援テスト」で物資支援→建設→完了記録と守備隊訓練を確認できる。教官派遣等の新しい訓練依頼は未実装で、守備隊の既存訓練処理を使用する。

- 編集原本は@game_dataの「イベント」シート。村計画・村依頼ひな型を定義し、村計画.json/村依頼ひな型.jsonを生成します。生成JSONを直接編集しません。SPREADSHEET_DATA_WORKFLOW.mdに従います。
- 新規依頼は村計画と実際の不足資源・守備を超える周辺脅威から生成。ひな型に合う実行中/待機中の計画を参照し、同じ討伐依頼を二重生成しません。
- イベント会話.jsonの選択肢や専用テストの固定依頼を新規候補へ加えません。問題解消で未受注の候補はなくなります。
- 周辺安全確保・守備隊補充・食料備蓄に加え、施設シート由来の建設計画を生成する。旧イベントの教会/奪還の試作計画自体は有効化しない。教会は施設前提と通常建設条件を満たす場合に施設候補となる。
- 依頼ひな型の現行2種は物資/討伐。数量上限・期限・クールダウン・完了効果は原本の値を使います。現在は友好度+10、期限15T、クールダウン5T。基本の金報酬を自動付与していません。

## 受注・進捗・支援報告

- フィールドの交流欄は村の情報・全受注件数と共通モーダルの入口のみ。受注・報告・休息等を直接実行する旧ボタンはありません。
- モーダルのクエスト一覧で左チェックを複数選択し、固定フッターからまとめて受注・支援報告します。チェックだけでは画面切替/受注/納品を行いません。
- 村ごと1件制限は撤廃。questLogByPlayerIdへ依頼別記録を保存し、questsByPlayerIdは旧保存の互換参照としてだけ維持します。
- 受注時に目標・対象ID・必要量・期限・元定義・合意報酬を固定。後から原本が変わっても進行中の条件を差し替えません。
- 討伐は受注時の対象IDで判定し、受注前の撃破を数えません。周辺の生存敵対的な敵の戦力が守備を上回るときに生成し、守護者/別ワールドの敵は通常村の対象外です。
- 納品は現在の選択拠点の残り必要量まで。部分納品は定義が許す場合だけ進捗を保存し、報酬は完了時だけ付与。既納品分は再請求しません。
- 同じ計画を別プレイヤーへ重複受注させません。同じ依頼の重複受注・完了後の再受領を拒否し、クールダウンを保存します。
- 一括受注/報告は選択分全体を原子的に実行し、途中で条件/報酬が不足すれば選択分全体を元に戻します。受注時の自動納品はしません。
- 期限失敗・警備/建設進捗・廃村化は全受注記録へ適用します。期限ターン以上では報告できません。

## 報酬

- 受注前に明示的な「交渉」で報酬変更画面へ切り替え、金・既知物資・人口を複数要求できます。取引と同じモーダル/バスケットを共用します。
- 合計価値・技能・友好度等で一度判定しAP20を1回消費。威圧は友好度-5。拒否から自動戦闘へ移行しません。
- 未受注の合意は5ターン有効。受注時に全品目をrewardTermsへ固定します。旧単独オブジェクトと新しい複数配列の両方を読めます。
- 完了時に村の実在庫/人口から選択中の自軍拠点へ全品目を移転。事前予約なし。一品不足なら納品・完了・報酬全体を確定しません。
- 人口は悪魔限定ではなく通常人口として受け取り、魂に自動変換しません。全種族の要求合計で村の最低残人口を保護します。
- 同条件判定は品目順を正規化し、同一品目の重複を合算。順番/交渉役変更で同ターン制限を回避しません。
- 変更は元の物資/旧魂報酬を置換し、友好度は維持。友好度は文字、物資/人口は共通アイコン＋数量で表示します。

## 村の計画

- 村のターンで実収入・維持費を在庫へ反映。主計画1件/待機2件を保存し、緊急計画へ切り替えても既存訓練・工事は進めます。
- 食料は目標期間の備蓄不足を検出し、純収入で期間内に解消できる場合は支援依頼を出しません。
- 墓地計画は領土内の有機死体/死体資源を契機とし、通常の条件・費用・枠・上限・工期・建設キューを共用。必要資材の不足1種を依頼し、実納品分を村在庫へ加えます。
- 他勢力が建設場所を取得した工事は進めません。完成施設は通常のフィールド表示・墓地保護判定に接続します。
- 守備兵不在でも人口が残れば通常守備軍1部隊を訓練補充。訓練期間は計画の目標ターン（未指定時config）。廃村/再入植は一般村防衛・廃村ルール.mdに従います。

## 旧保存と未対応の区別

- 番号付き会話の旧受注は、保存済み定義・適用済み番号・実行ID・元の費用/条件/回答を保ち、報告/支払い互換だけ維持します。新規受注方式には使いません。
- 未対応の条件・効果を無条件成立にせず拒否。旧魂報酬は受注保存の互換経路であり、新しい要求候補には出しません。
- 番号付きセルの編集書式自体はイベントシステム設計.mdを参照。書式が使えることと、一般村の新規クエスト生成元であることを混同しません。
- 継続守護/生贄契約の汎用締結、複合目標、貢献度別報酬、村研究の自動進行、種族別信仰施設選択、長期バランスは未対応です。専用事件テストの動作を一般イベント全体の完成と扱いません。

## テスト

- テスト操作→村・交流テスト→「会話・報酬交渉」：実食料不足と実在ウルフを置き、通常の生成で依頼を提示。悪魔向け固定依頼や番号付き追加候補はありません。
- 「村の計画・支援テスト」：墓地/食料不足/討伐/守備兵不在の4村。交流入口→クエストでチェック受注→再チェックで支援報告。1T経過で通常工事・訓練を確認します。
- 支援者4体・Lv30/移動120以上等の配置はconfig/v39-village-plan-test.json。村選択は選択ユニット/カメラ/交流先を変えるだけで、移動・納品・撃破を代行しません。
- check-v39-village-contact-entry.mjs：入口と旧操作撤去、全受注件数、村以外の固有行動。
- check-v39-progress-quests.mjs（check-v39-quest-batch.mjsも同じ検証）：実不足/脅威の生成、同時受注/保存/報告/巻戻し。
- check-v39-quest-rewards.mjs：単独旧形式と複数報酬の交渉/保存/一括支払い。
- check-v39-village-plan-playable.mjs：4村・通常モーダルの受注/報告・工事/補充・保存読込。
- 旧固定TEST_SHEET等の受注ボタンを前提にした過去テスト記録は、現行UIの検証成功を意味しません。

[UI53より前の記録](./history/village-ui-before-ui53/一般村イベント共通ルール.md)は履歴です。旧画面や旧生成元を復活させる根拠にしません。

## 村施設の完成表示（UI55）

- 村の施設も自軍拠点と同じ描画処理で建設中の画像/残りターンと完成画像を表示する。通常時は現在の視界内だけ、テスト時は全体を確認できる。地下へ地上の施設を投影しない。
- キュー完了時は建設中表示を除去し、完成施設へ切り替える。完成施設名/座標/ターンを村のplanSchedule.lastCompletedへ保存し、交流欄・情報タブ・計画テスト欄に表示する。古い保存に完成履歴がない場合も、既存buildingsを完成施設として表示する。
- 視界内またはテスト中の村の建設完了を建設ログへ1回通知する。同ターンの再実行や保存読込で再通知しない。残り0の未処理データは「完了処理待ち」とし、完成済みとは扱わない。
- 墓地の効果は領土内の新しい死亡による浄化低下を毎ターン2件/棟まで防ぐこと。既存死体の自動除去、放置/死の霧による低下の停止ではない。
- 検証: check-v39-village-plan-completion.mjs（390/1100）。実納品→実ターンで着工/完成、マーカー切替、完成ログ1回、情報/テスト欄、保存、視界外非表示を確認。
