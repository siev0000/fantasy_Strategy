# NPC勢力の開始と行動

更新: 2026-10-21 / UI65。

## 開始設定

- ゲーム開始設定の「ゲーム進行」にNPC勢力数（0〜8）を設ける。新規設定の初期値は2。一般村数、操作勢力数、参加者数とは別。
- `gameSettings.npcFactionCount` として設定・セーブに保持する。古い設定や、数を渡さない内部テストの開始は0とする。
- 通常の開始種族とクラス候補からNPC統治者を生成する。初期編成はヒーロー枠の統治者1体＋軍隊ユニット2体。単独の一般兵2人や、2つの部隊枠という意味ではなく、1駒に複数人が編成された通常軍隊を2駒支給する。
- 通常の `getV39UnitCreationOptions` / `inspectV39UnitCreation` から、開始時の軍事Lv・施設によって解禁されたクラス/army種別を読む。統治者と同じ基礎職を優先し、候補がなければ作成可能な基礎職へ。共通の軍隊初期Lv、装備、combatProfileの人数/HP倍率/攻撃回数、ユニット生成を使用し、通常の初期配置で別々のマスへ置く。未解禁の上位/精鋭軍隊へは変えない。
- 数は `config/v39-npc-faction-ai.json` の `initialArmies`（初期2）。配置前の開始時支給なので、資源/人口の徴兵支払いや訓練キューは発生させない。通常の徴兵制約を緩和したわけではない。既存セーブへ追加支給・既存兵の置換は行わない。テストの「勢力追加」は既存編成の複製用途を維持する。
- 人の初期配置後、NPCの拠点を自動配置する。配置不能なら拡大/勢力数削減の案内を出す。人の担当勢力や操作順へNPCを加えない。
- ローカルと通信ホストの開始状態生成は同じNPC生成を使う。通信ではホストの生成済み状態を配布する。

## 行動方針

### 役割の分離（2026-10-21 / UI67）

- 勢力NPCはプレイヤーに相当する競争相手。探索・領土拡張・戦力増強・覇権地の確保を進め、勝利を目指す。
- 一般村NPCは地域の生活・発展・防衛と、依頼/取引/交流を担う。勢力NPCと同じ勝利競争AIを適用しない。建設や資源計算などの基礎処理は共用してよいが、役割・目標・報酬を同一にしない。
- 村として配置された天使・悪魔・ヴァンパイア等は、通常の村とは異なる強力な特殊勢力として扱う。ただし勝利は目指さない。一定ターンごとの生贄の奉納により、仲間への加入や対応する種族への変異が可能になる立ち位置。
- 加入対象は軍隊ユニット。基本は1駒を配下に迎え、生贄の量を増やすと2駒、3駒と契約数を増やせる。軍隊内の人数を増やす意味ではなく、村全体が配下になる意味でもない。定期奉納は加入済みの軍隊を維持する費用で、奉納ごとに軍隊を追加生成しない。
- 役割は種族だけで決めない。同じ種族が競争勢力として生成された場合まで、勝利を目指さない村へ変更する意味ではない。村/勢力の分類と種族の性質を分離する。
- UI67では軍隊加入・定期奉納を実装。自拠点の生体住民を指定して人口から差し引く。UI68では交渉者本人の転生（対応種族Lv3・主要種族切替）を追加。詳細と暫定調整値は [特殊村・奉納契約ルール](./特殊村・奉納契約ルール.md)。捕虜/配下を個別指定する奉納、NPC勢力が自動でこの加入契約や転生を行う方針は未実装。既存の人口用魂への即時変換や一般村への生贄要求とは別契約。

- 人の操作終了後の既存AIフェーズで行動する。一般村とは別の国・拠点・部隊を持つ。
- 未発見の覇権地は目標に使わない。発見した未確保の覇権地を優先し、既存の奥地入場・攻略・退出・取得処理を使う。
- 取得した地点は確保期間中または妨害中に防衛目標とする。同じ勝利判定が人とNPCを評価する。
- 攻撃可能な敵がいるときは探索でAPを使い切らず、戦闘へ回す。対象がなければ移動して視界を広げる。隠れた資源の調査を探索前の定型処理としては実行しない。地上/奥地の座標や退出待機を混同しない。
- 訓練を建設より先に判定する。生存ユニット+訓練待ちの目標数は当面6で、`config/v39-npc-faction-ai.json` から変更可能。
- 建設候補は施設シートの前提施設・基礎優先度を使用し、防衛・探索に加点する。食料不足時は食料施設とその前提となる墓地の優先度を上げる。通常の研究・地形・費用・枠・工期を満たす必要がある。
- 同施設を際限なく増設せず、拠点の建設キューがある間は次の建設を開始しない。村と共通の前提判定は `v39-facility-development-rules.js`。

## 実行元と確認

UI66では行動目標に加え、建設・戦力増強・不足資材を表示する。`v39-npc-development-plan.js` の共通判定を実際の建設/徴兵と診断用計画に使用する。実行後の状態から次の候補を保存し、UIは `aiState.developmentPlan` を読むだけ。旧セーブ等で計画がない場合は次のAI行動で判断する。

- 建設: 選択拠点の建設中施設/残りT、または実行可能な次候補。実行可能候補がない場合は、資材以外の障害が少ない候補を優先順位順に表示し、条件待ちであることを明示する。建設中の次候補は完成後に判断。資材は代替素材を解決した実費用で比較する。
- 戦力: 生存＋訓練中と `unitTarget`（初期6）を比較。通常軍隊を優先する既存候補順と作成条件を共用し、種族/職業/軍隊か個体か/完成Lv、人口・軍事Lv・上限等の不足条件を表示する。1軍隊は人数に関係なく1駒。訓練予約で目標に達していれば「訓練完了待ち」とする。
- 求める資材: 建設/戦力増強/魂・死体による人口増加の用途別に在庫/必要量と不足を表示。同じ資源を用途別に示し、同時支出を予約した合計ではない。表示は直近AI判断時点。新たな自動調達・取引行動を追加したものではない。

検証: `scripts/check-v39-npc-development-plan.mjs`（資材不足→補充→実建設/訓練、建設中、戦力目標達成、保存読込、390/1100の診断、表示によるAI無変更）。

テストON時は「テスト操作 → 診断 → NPC勢力診断」の横タブから1勢力ずつ切り替える。現在プレイヤーの視界では絞らない。「現在の目標」を独立枠で示し、対象名/座標/必要資源、拠点数/生存数/訓練数、直近コマンド/完成施設、所属ユニットの軍隊人数・Lv・ワールド・座標・HP/APを読む。目標が未決定なら未設定と表示する。表示するのはAIが保存した現在目標で、診断を開くことでAIを動かしたり目標を再抽選したりはしない。

選択は状態更新でも維持し、対象勢力が消えたときは残る最初の勢力へ戻る。タブは左右/Home/Endキーでも切替可能。「前回処理ターン」は通常表示から除外。`aiState.lastProcessedTurn` は同ターンにAIが二重行動しないための内部判定として維持する。敵AI診断は野良と村守備軍向けのまま。NPCなしの場合も未登録の案内を表示する。

開始画面は `v39-field-settings-final.js`、生成は `v39-game-state-bridge.js`、自動配置は `v39-initial-placement.js`、行動は `v39-faction-ai.js`。同じ処理を別の画面やタイマーへ追加しない。

`scripts/check-v39-npc-start.mjs` は390/1100で入力から生成、NPC2勢力の配置、人のみの担当/ターン、保存読込、設定再表示、実ラウンドのAI、発見済み覇権地の目標、NPC0を確認する。既存のlocal-session、faction-ai-objective、faction-ai-explorationも使用する。

## 魂・死体を求める方針

- `config/v39-npc-faction-ai.json` の `resourcePatterns` が行動パターン。`standard` は追加行動なし、`soul-hunter` は増加条件「魂」、`corpse-hunter` は「死体」に対応する。種族名ではなく既存の人口用クラス定義を読むため、悪魔/デヴィル、吸血鬼/ヴァンパイアの別名も共通解決する。同じ増加条件の他種族にも自動適用される。
- `racePatternIds` で種族別にパターンIDを指定できる。例: `{"エンジェル":"standard"}`。勢力単位の `factionState.aiState.behaviorPatternId` があればそれを優先する。`standard` を指定すると強制停止。設定対象は新規生成だけでなく既存NPCにも適用される。
- 不足判定は配置済みの各拠点の住民種族と実在庫。基準は `minimumStock`（初期1）と、次の人口増加に不足するゲージを既存の資源価値へ換算した量の大きい方。別拠点の在庫を合算せず、同拠点・同資源の需要は重複計上しない。
- `actions` の配列順に `recover`（発見済み残留品）、`demand`（既知村への生贄要求）、`raid`（既知勢力への襲撃）を評価する。順序変更/項目削除が可能。確保期間中の覇権地防衛を最優先し、具体的な資源目標があるときは新たな覇権地攻略より優先。供給元未発見の探索だけを理由に覇権地攻略を止めない。
- 残留品は人と共用の `recoverV39GroundLootState` で実際に消費し、所属部隊の荷物へ移す。拠点へ帰る通常AP移動を行い、既存 `depositV39PlayerCargo` で納庫する。遠隔取得や在庫の自動生成は行わない。
- 村は現在の視界か接触記録で認識したものだけ。廃村・属国・敵対村・他勢力の契約済み村を除外。地上の生存ユニットが村の中心から1マス以内に到着したとき、共通交渉AP20と威圧技能/周辺攻撃力/守備軍攻撃力で成否を判定する。`sacrificeDemand` が仮の確率・技能係数・戦力係数・友好度低下幅。成功は既存 `sacrificeContract`、失敗も試行時点と `demandCooldownTurns`（初期5）を保存する。AP不足/同条件同ターン/待機済みは拒否する。
- 契約しただけで村人を消したり魂・死体を在庫へ加算したりしない。既存の休息強襲/救援分岐（契約先との友好度しきい値）へ接続する。村が実際に保持している捕虜・死体を受け取る処理はUI62で通常プレイ/NPCへ共通化した。保管庫の合成専用魂は人口用の魂在庫とは別で、勝手に消費しない。定期的に村人を供給する仕組みは未実装。
- 襲撃は既知勢力のみ。`allowWar` が有効なら既存 `declareV39War` を使って宣戦し、既存戦闘/反撃/死亡処理へ渡す。同盟/不可侵の有効期間中は選ばない。戦争成立だけで魂や死体は生成しない。戦後の残留品が発見されれば通常回収へつながる。野良の無差別狩猟や村への拒否即襲撃は今回追加しない。
- 調査は隠れた資源等を発見する独立行動。コマンド/APIと既存のAP/進捗/完了処理は維持するが、UI64以降は通常NPCの探索にも自動で付けない。NPCが経済目的で調査を開始する別方針は今回追加していない。開始済みの調査を消したりAPを払い戻したりはしない。
- 目標/試行結果/宣戦/回収は既存NPC診断のコマンドに表示。契約・試行期限・行動履歴・荷物は通常セーブに保存する。

`scripts/check-v39-npc-resource-policy.mjs` はViteの5173（`V39_POLICY_TEST_URL`で変更可能）で、既存データによる魂/死体判定、通常方針への切替、未発見情報の除外、要求の成功/拒否/AP/再試行、条約除外/実宣戦、残留品の実回収、実AIイベント・保存読込・通常納庫、390/1100の診断表示を確認する。通常方針の既存目的/探索テストは明示的にstandardを指定して比較する。

戦力の精密評価、拠点昇格の計画、長期の供給量/勝率調整は今後の対応。今回の確認は複数NPC間の長期勝率や完全攻略のバランスを保証するものではない。

## 暫定の魂への即時変換

- `config/v39-soul-conversion.json` の `enabled`（初期true）で切替。`receiverClassNames`（エンジェル/デヴィル）を人口用種族定義の名前と比較し、天使/悪魔の表記にも対応。受取勢力の種族で判断し、配下に天使が1体いるだけでは対象にならない。`soulsPerPerson` は初期1。OFF後も既に変換済みの魂や受取履歴は巻き戻さない。
- 契約先の実際の `heldUnits` を、地上の中心から1マス以内で受け取る。プレイヤーは村の会話タブの「生贄を受け取る」→フッターで実行。NPCは保有契約に未受取対象があれば同じ `receiveV39VillageSacrifice` を使う。元の対象を村から除き、適格な1体につき人口用魂1へ変換、受取ユニット/部隊の荷物へ入れる。装備も荷物へ分離し、既存の通常移動・拠点納庫を使う。受取自体の追加APはない。
- 対象のID/所有者/受取村/ターン/魂数を `sacrificeReceiptHistory` に保存。村内の重複IDと受取済み対象の再受取を防ぐ。自分の拘束ユニットは受取対象にしない。アンデッド/召喚体/魂回収済み対象からは魂を生成せず、変換OFFや対象外勢力と同様に `villagePrisoners` へ装備なしで保持する。履歴・荷物・保持対象は通常セーブに保存する。
- 村の人口報酬も同じ種族/比率/切替を使用し、天使・悪魔へは魂を受取拠点へ加算する。村側の実人口を減らし、受取側の人口は同時加算しない。通常勢力とアンデッド種族の人口報酬は従来の人口移転。報酬欄は変換後の魂アイコン/個数で表示し、元の人口報酬をツールチップで説明する。
- 野戦で敵を倒しただけの自動変換、保管庫の魂の消費、全村人の自動供給、定期輸送は追加していない。変換能力をスキル条件へ変更するのは後続。

検証: `scripts/check-v39-soul-conversion.mjs`。5173で条件・ON/OFF・種族別名・元装備・二重受取・通常人口報酬を確認し、3000の配信ビルドで会話からの受取、保存読込、実AI受取→荷物→帰還時納庫を確認する。390/1100の画面は `output/web-game/soul-conversion`。

## 移動探索と資源調査の分離

- UI63: 魂/死体が不足し、既知の回収先・村・襲撃先がない `resource-search` は、その場の調査を開始しない。APを使って未踏の視界へ向かう。調査済みマスかどうかと、既に見渡したマスかどうかは区別する。既に開始済みの調査を勝手に消したりAPを払い戻したりはしない。
- 既存の `visibility.exploredTileKeys` と現在の実視界を使い、踏査済みで到達可能な土地から未踏境界までの経路を探す。近い未踏領域へ向かうため、調査未実施の隣マスを無条件で往復する処理にはしない。村の位置や未発見資源を目標には使わない。
- 部隊の移動AP・地形・高度・占有・災害通過ダメージを既存処理で検証。`scouting.maxStepsPerTurn`（初期6）以内でAPが続く限り移動し、各歩で視界/既知勢力を更新。村等の具体的な供給候補を認識したら探索を止めて既存の接近/要求/回収目標へ切り替える。到着済みかつAPが残れば同じAIターンに要求できる。戦闘可能時は戦闘を優先する。
- 経路の探索ノード数は `scouting.searchNodeLimit`（初期512）で制限。同一部隊の重複探索を避ける。踏査履歴は通常セーブへ保持し、配下の人数分に別履歴を増設しない。旧 `resourceScouting` 設定も読込互換として残す。
- UI64: 通常 `explore` と供給元 `resource-search` が同じ `scoutNpcMap` を使う。移動の候補選択から `surveyedTileKeys` の依存も除外し、「調査済みだから探索しない」という混同をなくす。通常探索でも目的や覇権地が認識されたら移動を止めて目的を切り替える。
- `scripts/check-v39-faction-ai-exploration.mjs` は通常探索で調査を開始しないこと、複数歩/次ターン継続/AP消費、全マス調査済みでも経路が同じこと、独立した調査コマンドの実行を確認する。`scripts/check-v39-npc-move-scout.mjs` は配信3000で供給元探しの調査なしの複数歩/AP消費、移動中の村発見→要求切替、視界外の村を使わないこと、次ターンと保存後の踏査履歴、390/1100の診断を確認する。
