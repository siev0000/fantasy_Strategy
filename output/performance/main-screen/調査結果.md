# メイン画面の負荷調査（2026-10-04）

ソース実装は変更せず、ローカルVite・Chromium headless・1280×900で計測。実ゲームの生成/配置/敵出現/ターン処理を使用。単一プレイヤー7ユニット、realistic、固定シードperf-main-{サイズ}。初期統治者と1村を計測用に設定。イベントリスナー時間計測あり。実機スマホ/本番配信/複数ターン平均ではないため、時間は比較・原因特定用であり保証値ではない。

## 実測

|項目|60×60・92敵|100×100・256敵|
|---|---:|---:|
|同じ値を設定する状態更新1回（3回平均）|180ms|407ms|
|活動ログ1件追加|180ms|375ms|
|全状態取得（ターン前、10回平均）|5.42ms|11.9ms|
|全状態取得（ターン後、10回平均）|15.8ms|42.0ms|

|Worker判断計算合計|0.262秒|1.205秒|
|AIメイン側反映|4.40秒|24.12秒|
|AI結果の描画反映待ち|1.61秒|10.97秒|
|演出処理（表示対象は両方0件）|1.49秒|14.52秒|

各計測区間は排他的な全区間分解ではない。表の数値を単純加算しない。待機中は平均16.4～16.5ms/frame。この条件では常時描画より更新時のCPU負荷が支配的。JSヒープの表示だけから総メモリやVRAMは判定できない。

## 原因と対策（優先順）

1. **全状態のコピーを繰り返す取得API**
   - frontend/src/v39/core/v39-game-state-bridge.js getState(272)、setState(329)、normalizeState(176)。読むだけでも敵/巣/全プレイヤー/探索マップを複製・正規化。書き込みでも全体正規化、変更イベントのstate作成、返り値のstate作成を行う。
   - currentV39TurnNumber()（frontend/src/lib/v39-turn-timing.js:24）はターン番号1個のために全状態取得する。AIの判断ログにも各アクションごとに使われる。
   - 対策: timeline/activeFaction/enemy等の対象別読み取り、処理単位の共通スナップショット、コピーは更新境界・保存境界へ限定。単純に生参照を公開すると外部書き換え事故になるため、読み取り専用契約と不変更新を整える。
2. **演出を表示するかの判定だけで全体取得を反復**
   - frontend/src/v39/ai/v39-enemy-turn-presentation.js visibleEnemyEvent内で移動イベントごとにgetV39GameState()して生死を検索する。100マップは380行動イベント、表示対象0件でも14.52秒。
   - 対策: 開始時に生存敵IDのSet/Mapを一度作り、視界の既存スナップショットで判定。実際に再生する時のみ対象1体を再確認する。
3. **洞窟対応が地上ターンにも全マップ保存/復元を繰り返す**
   - frontend/src/v39/core/v39-world-context.js withV39WorldContextとv39TurnWorldIds。各段階の前後でcapture/getState/setStateし、同じ表示マップにもコンテキスト切替を行う。
   - frontend/src/v39/core/v39-cave-world.js rememberWorldはexplorationWorlds全体をcloneし、表示中マップの配列と空間データを再コピー。
   - 対策: 表示中マップは直接処理、非表示マップだけ切替。ターン始終/所在切替/セーブのタイミングに保存をまとめ、変化したworldだけ差分更新。洞窟追加により地上の負荷も増える構造であり、優先して回帰を修正する。
4. **変更内容に関係なくUIを重複更新**
   - game-state-changedの購読箇所24。行動欄はgame-state-changed/squad-detail-rendered/unit-selectedで重複する。
   - frontend/src/v39/combat/v39-combat.js renderActionPanel(431)はボタンごとにactiveFaction/currentV39TurnNumberを再取得。
   - frontend/src/v39/unit/v39-squad-derived-binding.js scheduleRender(599)は予約済み判定なしでrequestAnimationFrame(render)。部隊詳細のinnerHTMLを作り直す。
   - 対策: 変更対象キー/リビジョンをイベントに付ける。1フレーム1回へまとめる。HP/APなどは部分更新。非表示のタブ・モーダルを更新しない。行動欄内はfactionとturnを1回取得。
5. **視界・マーカーは描画をスキップしても前段の計算/複製が残る**
   - frontend/src/v39/map/v39-map-visibility.js renderVisibilityLayers(567)は視界・検出計算後に署名比較。
   - frontend/src/v39/map/v39-map-entities.js renderMarkers(864)も全状態取得後に署名比較。
   - 対策: ユニット位置/索敵/領土/地形等の関連リビジョンを先に比較。無関係なログ更新では計算自体をしない。

## 補足

- 地形/高低差/FogのRenderTexture化は既にあり、先に再実装するのは適切でない。
- 100×100は62×74pxタイル、半解像度キャッシュで約8.8百万画素/層。RGBA単純換算で約35MB/層。複数層・画像・GPU用バッファは別途ある。これは理論的な画素容量で、実測VRAMではない。スマホ向けにはチャンク化/画面周辺だけの保持が次候補。
- 20敵に限定し演出関数を一時的に無効化する別計測でも60×60ターンに7.50秒、Worker判断27.7ms、メイン反映571ms。計算だけをWorkerへ移しても周辺コピーが残ることを確認。
- 主な計測にpageerrorなし。full-population-report.jsonが通常敵数の実測、report.jsonが20敵・演出無効の切り分け計測。probe.mjs/ai-probe.mjsで再現可能。
- ゲーム仕様・JSON・ソースは未変更。修正は1～3、次に4～5の順を推奨する。
